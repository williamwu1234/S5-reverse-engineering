# BLE 凭据链打通：先写身份、再读数据（2026-10-13，**重大更正**）

> 本文件推翻了 `14_` / `15_` 号报告中"BLE 读取需要配对/绑定"的结论。
> 真相是：**相机要求的只是 App 的协议顺序——先写身份，再读数据**。

## 1. 之前为什么读不到

`14_` / `15_` 号报告记录的现象是：**连接 + 枚举 GATT 正常，但任何属性读都会让相机立刻断链**。
当时的推断是"需要 BLE 绑定（链路加密）"，并据此撤回了"无认证泄露凭据"的安全结论。

**这个推断是错的。** 真相在 APK 的连接顺序里（`E5/j.java`、`C5/e.java A()`）：

```
连接 → 注册通知(本机无 CCCD，自动跳过) → 读 INITIAL_INFORM …   ← 这是 APS 分支
                                         写 DLNA_UUID + FRIENDLY_NAME  ← 非APS 分支在【读之前】就写
```

我们此前**没打招呼就直接读**，相机把这种乱序访问当入侵，直接断链。

## 2. 正确的顺序与实测结果

`04_工具与脚本/campaign2/ble_write_then_read.swift`（编译产物 `ble_wr`）：

```
[A] 连接 + 枚举（9 服务 / 41 特征）              ✅
[B] 写 8D08A420 = 原始 DLNA_UUID 字节            ✅ 写回调 成功
    值 = 4d454930010010008001020000025ad6
    （= "4D454930010010008001" + seed，与 APK H5/p.java A() 同构）
[C] 写 CD7A71A0 = 原始设备名 "MacBLE"            ✅ 写回调 成功
[D] 读 03E23A31 (idx35 INITIAL_INFORM)          ✅ raw=b6b76439 → 会话密钥 0xB6B76439
[E] 读 E206A5C0 (idx5 CAMERA_SSID)              ✅ raw=53352d373045323533… → "S5-XXXXXX"
[F] 读 C97CF1A5 (idx6 CAMERA_WIFI_PASSWORD)     ✅ 见 §3
```

**注意 [B] 与 [C] 是"原始字节写入"，不是 `H5/s.b()` 编码后的值** —— 因为 S5 **没有**
`bb5d2a8c`（APS 特征），`isUUIDApsSupported=false`，App 走 `E5/j.java` 的 **else 分支**：

```java
} else {
    y(1, s());   // 写 8D08A420 = g.v0() 原始字节
    y(2, t());   // 写 CD7A71A0 = g.w0() 原始字节
}
… 之后才 x(35) 读密钥
```

## 3. Wi-Fi 密码：为空（两次独立验证）

两次独立采集（**不同的会话密钥**），密码特征返回的原始字节都是"**会话密钥的字节反转**"重复：

| 采集 | 会话密钥 | 密码特征原始字节（节选） | 解码结果 |
|---|---|---|---|
| #1 | `0xE476D61A` | `e476d61a` ×16 + `1b89291a` | `00000000…` → **空** |
| #2 | `0xAAA00275` | `aaa00275` ×16 + `555ffd75` | `00000000…` → **空** |

`H5/s.a()` 的解码是 `swap32(LE32(raw)) ^ key`：

```
swap32(LE32(e476d61a)) = 0xE476D61A ,  XOR key 0xE476D61A  =  0x00000000
```

⇒ **明文就是全 0**（空密码），**不是密钥算错**（错密钥会解出乱码，而这里精确为 0）。

这与 Windows 侧的信标解析（`capability=0x0401`，Privacy 位 = 0，无 RSN/WPA IE）
以及本项目实测的 `accctrl → …,remote,open` **三方吻合**：
**相机 SoftAP 是明文开放网络，密码为空**。

## 4. ⚠️ 安全结论（**二次更正**）

`15_` 号报告曾撤回"无认证泄露 Wi-Fi 凭据"的结论。**现在必须再改回来**：

> **已实机确认：任何在 BLE 范围内的设备，无需配对、无需 PIN、无需机身确认，
> 只要按正确顺序（先写身份、再读），即可读出相机的 Wi-Fi SSID 与密码。**

- 身份写入用的是**明文、任意值**（`8D08A420` 写什么都没校验），**不构成认证**。
- 本机密码为空；但在**配置了 WPA2 的相机**上，该特征会返回**真实 Wi-Fi 密码**——
  攻击者据此可接入相机热点，进而接触完整的 `cam.cgi` 控制面。
- 这是**实打实的未认证凭据泄露**，而不是"需要绑定的安全设计"。

**建议**：把这条作为独立发现上报（Panasonic LUMIX Sync BLE 凭据交付无认证）。

## 5. 稳定性：需要重试

相机的 BLE 握手**不稳定**：多次尝试中，有的在写完身份后立刻断链（约 1/2 概率），
有的则顺畅跑完全程。实测统计：

| 尝试 | 结果 |
|---|---|
| 1 | ✅ 完整（读到 SSID + 密码） |
| 2 | ❌ 第 2 步后断链 |
| 3 | ✅ 完整 |
| 4 | ❌ 第 2 步后断链 |

⇒ 已把工具做成**可重试**（`s5ctl.sh` + 循环）。推测相机对"单位时间内只受理一次握手"
或"上一次会话残留"敏感；重试即可稳定拿到数据。

## 6. 与本项目其它结论的关系

| 既有结论 | 本次影响 |
|---|---|
| "BLE 读取需要绑定"（14/15 号） | ❌ **推翻**，是协议顺序问题 |
| "BLE 无认证泄露凭据"（15 号初版） | ✅ **恢复并实机证实** |
| "相机热点是开放网络 / 密码为空"（17/18 号） | ✅ 三通道交叉印证 |
| `req_acc` 返回 `err_user_refused`（18 号） | 与 BLE 无关：**Wi-Fi 控制面的 accctrl 门是有效的**；但 **BLE 凭据读取是敞开的** |

**两条安全结论并不矛盾**：
- **Wi-Fi 控制面**（`cam.cgi`）：有访问控制门，陌生人拿不到控制权 ✅
- **BLE 凭据面**：无认证，陌生人可读出 Wi-Fi SSID/密码 ❗

后者是前者的大门钥匙——**只要热点密码非空，Wi-Fi 那道门就被绕过了**。
