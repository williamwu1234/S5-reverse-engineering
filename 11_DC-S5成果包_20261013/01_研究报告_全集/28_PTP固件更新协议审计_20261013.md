# PTP 固件更新协议审计（0x9603 / 0x9605 / 0x9606 / 0x9607 / 0x9406）

2026-10-13 · 纯离线逆向（LUMIX Tether 2.12 arm64）+ 实机只读验证
承接：`27_ROM_BACKUP导出成功与数据解析_20261013.md`

---

## 0. 结论

| # | 结论 |
|---|---|
| **1** | **固件更新协议完整还原**：相机经 `0x9605` 给出 `{Status, Address, Size}`，客户端用 `0x9606`+`0x9607` 按该地址写入 |
| **2** | **`0x9406` 的 8 个子码全部定位**，其中 **`0x00090013`（FWUP Request）** 与 **`0x00090014`（UPDATE）** 是**此前映射表里没有的** |
| **3** | **要拿到"地址"必须先发 `0x9406/0x00090013`（升级请求）** —— 该动作**很可能先擦除目标区域** |
| **4** | ⇒ **本路线判定关闭**：达到"可测试状态"所需的动作本身就是**高砖机风险**，而收益上限只是"把已签名固件写到错误地址"（**拿不到执行自编代码的能力**） |
| **5** | 该判定与项目自身红线一致：*"永不发送 `0x9406` 子码"* |

## 1. 协议链路（完整）

```
0x9605 Get_Event_Info   → 相机返回 { Status, Address, Size }
         ↑ 地址的【唯一来源】。空闲态返回 12 字节全零 = 未就绪
0x9606 Send_Data_Info   → 客户端回送 [Size][Address][DataType]
0x9607 Send_Data        → 500 KiB 分块数据
```

### 1.1 `0x9606` 负载布局（反汇编还原）

```
32 位路径: [TrnsferSize:4][Address:4][DataType:4]   = 12 (0x0c) 字节
64 位路径: [TrnsferSize:4][Address:8][DataType:4]   = 16 (0x10) 字节

来源: Lmx_func_api_fwup_Send_FWUP_Data
  32 位: stp w21, w24, [x29,#-0x70]  ; +0=size, +4=address
         stur w22, [x29,#-0x68]      ; +8=datatype
  64 位: stur w21, [x29,#-0x70]      ; +0=size
         stur x24, [x29,#-0x6c]      ; +4=address (8 字节)
         stur w22, [x29,#-0x64]      ; +12=datatype
```

### 1.2 **地址不是协议参数，而是相机给的**

```asm
Lmx_func_api_fwup_Send_FWUP_Data:
  ; 64 位分支
  adrp x8, 0x49e000
  ldr  x24, [x8, #0x744]        ; ★ 地址 = 全局变量 @0x49e744
  ; 32 位分支
  ldr  w24, [x8, #0x730]        ; ★ 地址 = 全局变量 @0x49e730
```

该全局由 `Lmx_lib_ptpif_LmxExt_Get_Event_Info`（`0x9605`）的响应填充
（日志串 `"RedyInfo:Address : 0x%016llx"` / `"0x%08x"`）。

**⇒ 用官方 Tether 无法测试任意地址（硬编码常量）；但自定义客户端在协议上可以改写回送值。
相机是否会校验这个回送地址 —— 未知，且需要先进入"更新就绪"态才能测。**

### 1.3 `0x9605` 响应布局（反汇编还原 + 实机验证）

```
offset 0x00 : Status  (u32)   0 = 未就绪
offset 0x04 : Address (u32/u64)
offset 0x08 : Size    (u32)
```

**实机验证（本次，只读）**：

```
0x41000012 → rc 0x2002 (GeneralError)   无数据
0x41000013 → rc 0x2001  20 字节: 13 00 00 41 | 0c 00 00 00 | 12 字节全零
0x41000014 → rc 0x2001  20 字节: 14 00 00 41 | 0c 00 00 00 | 12 字节全零
0x41000015/16/17 → rc 0x2002
```

载荷结构 = `[event_id:4][len=0x0c:4][{Status,Address,Size}:12]`，**全零 = 空闲态无待升级** ✅

## 2. `0x9406` 子码全表（**本次补全**）

| 子码 | 功能 | Tether 包装函数 | 项目旧表 |
|---|---|---|---|
| `0x00090011` | MenuSave（菜单配置保存） | `Setup_Ctrl_MenuSave` | ✅ 有 |
| `0x00090012` | SD_Format（格式化 SD） | `Setup_Ctrl_SD_Format` | ✅ 有 |
| **`0x00090013`** | **FWUP Request（升级请求）** | **升级线程内联，无独立包装** | ❌ **本次新增** |
| **`0x00090014`** | **FWUP UPDATE（开始烧写）** | **升级线程内联** | ❌ **本次新增** |
| `0x00090015` | SensorCleaning（除尘） | `Setup_Ctrl_SensorCleaning_Req` | ✅ 有 |
| `0x00090016` | PixelRefresh（坏点刷新） | `Setup_Ctrl_PixelRefresh_Req` | ✅ 有 |
| `0x00090017` | FirmUpAbort（升级中止） | `Setup_Ctrl_FirmUpAbort_Req` | ✅ 有 |
| `0x00090018` | ResetSetting（全量重置） | `Setup_Ctrl_ResetSetting_Req` | ✅ 有 |

> **注意**：Tether 里**没有**"升级开始"以外的独立包装 ——
> `0x13`/`0x14` 是**直接内联在 `LMX_func_api_FirmwareUpdate_Th` 里**的，这也是旧映射表漏掉它们的原因。

## 3. 固件更新状态机（完整）

```
[FWUP_READY]   ← 相机就绪；★ 只有到这个状态，0x9605 才返回非零 Address/Size
      ↓  Setup_Ctrl(0x00090013)  "FWUP Request"     ← ★★ 让相机准备接收（疑似先擦除）
      ↓
[FWUP_STATUS_DATA_TRANSFER]
      ↓  0x9606 (Send_Data_Info) → 0x9607 (500 KiB ×N)
      ↓  Setup_Ctrl(0x00090014)  "UPDATE"           ← 让相机开始烧写
[FWUP_STATUS_UPDATE]
      ↓  等待 "FWUP Update cmp event"
```

相关日志串（佐证）：
```
"%s FWUP : ERROR : FWUP Request Response"
"%s FWUP : OK : ... FWUP_PROGRESS 2 -> [LMX_FWUP_STATUS_DATA_TRASFER]"
"%s FWUP : OK : ... FWUP_PROGRESS 3 -> [LMX_FWUP_STATUS_UPDATE]"
"FWUP : Wait FWUP Update cmp event..."
```

## 4. 为什么关闭这条路线

| 项 | 评估 |
|---|---|
| **必须要的动作** | `0x9406 / 0x00090013`（FWUP Request）—— 让 bootloader **准备接收固件** |
| **它大概做什么** | 这类流程**通常先擦除目标区域** ⚠️ |
| **若擦除后不写（或写不进）** | **相机可能再也开不了机** ⚠️⚠️⚠️ |
| **兜底** | ❌ 无 —— 项目自己判定 SD.DAT 恢复模式"有砖机史、不可逆" |
| **收益上限** | 写入数据仍**必须过签名校验** ⇒ **拿不到执行自编代码的能力** |
| **与项目红线** | 一致：*"永不发送 `0x9406` 子码"* ✅ |

> **判定**：这是典型的**"擦除即变砖"**风险，而收益只是"看一眼地址"。
> **不发。本路线关闭。**
