# BLE 身份注册 vs Wi-Fi accctrl 门：两者独立（2026-10-13）

> 回答"能否用电脑像 App 一样稳定地与相机通信"以及"BLE 注册是不是 Wi-Fi 授权的钥匙"。

---

## 0. 结论速览

| # | 结论 | 强度 |
|---|---|---|
| 1 | **局域网（station）方式完全可行且稳定**：Mac 不切网、不看门狗、不依赖手机 | ✓ 实测 |

| 5 | ⇒ **两道门互相独立**：BLE 凭据面敞开，Wi-Fi 控制面仍需授权 | ✓ 实测 |

## 1. 为什么要改用局域网（station）

连相机热点（SoftAP）这条路**极不稳定**，实测统计：

| 现象 | 出现次数 |
|---|---|
| `Failed to join network S5-XXXXXX. Error: -3970` | 12+ 次（含射频重置后） |
| `-3906` | 3 次 |
| `Could not find network`（热点瞬间消失） | 4+ 次 |
| 成功关联 | 3 次（06:30 / 06:39 / 07:18） |

原因有三层：
1. 相机 SoftAP **单客户端**，手机或残留会话会挡住；
2. macOS 发现该网络**无互联网**时**自动回落到家网** → 探测全部超时；
3. 相机 SoftAP 本身时开时关（广播不稳定）。

**转机**：让相机作为 **station 连家庭路由器**，Mac 留在家里网——`192.168.x.x` 直接可达，
**无需任何网络切换**。项目前期（`persist.py`、配置块读写、47 个设置域审计）本来就是这么做的。

## 2. 本轮实测（局域网，全程不切网）

工具：`04_工具与脚本/campaign2/ble_lan_pair.swift`（编译产物 `ble_lan_pair`）

```
目标 IP=192.168.x.x  seed=020000025AD6  UUID=4D454930-0100-1000-8001-020000025AD6
编码自检 encodeString("ABC",0x9032782C) = d33b70d1

[BLE] 发现 S5-XXXXXX rssi=-49 → 已连接 → 枚举 41 特征
[BLE] 写身份 DLNA_UUID = 4d454930010010008001020000025ad6
      ← 写回调 8D08A420 err=成功                    ✅
[BLE] 写设备名 → BLE 断链（身份已写完）

[Wi-Fi 阶段]
基线 req_acc  → err_user_refused,S5-XXXXXX,remote,encrypted
req_acc_g     → err_param            ← 无密钥
req_acc_e     → err_param            ← 用 key=0 编码后仍被拒
+0s 轮询      → ok_under_research,S5-XXXXXX,remote,encrypted   （状态在跳）
getstate      → err_reject
getinfo capability → err_reject
getinfo lens  → err_reject
getsetting videoformat → err_reject
req_acc_can   → err_critical
```

**判读**：
- BLE 注册**确实成功了**（明文写入，无任何认证）。
- 但 Wi-Fi 侧基线就报 **`err_user_refused`** —— 相机认为"用户未同意"。
- 所有读端点仍是 **`err_reject`**，**门没有打开**。
- `req_acc_g` 在本机固件上**不存在**（`err_param`），因此 APK 里那条
  "encrypted → 用密钥编码 UUID/名字走 `req_acc_e`" 的路径**在这台机器上走不通**。

⇒ **BLE 注册 ≠ Wi-Fi 授权**。相机对 Wi-Fi 控制面的门是**独立**的，
需要**机身侧动作**（确认/进入"等待应用"状态），而不是靠 BLE 递身份。

## 3. 与既有结论的合并

| 面 | 结论 |
|---|---|
| **Wi-Fi 控制面**（`cam.cgi`） | 有独立访问控制门；陌生客户端拿不到控制（`err_user_refused` / `err_reject`）✅ |
| **BLE 凭据面** | **无认证**：可读出 Wi-Fi SSID/密码（见 19 号报告）❗ |
| **两者的关系** | **不连通** —— BLE 注册的身份打不开 Wi-Fi 门 |

19 号报告里"BLE 凭据是 Wi-Fi 大门的钥匙"这一推论，**仅在某些相机确实用热点密码作为唯一门槛时成立**；
对本机而言，**`cam.cgi` 还有一层独立于密码的访问控制**，所以那把"钥匙"开不了这道门。
（本机热点密码为空，因此该钥匙本来也无意义。）

## 4. 工程建议（后续一律照此做）

1. **相机保持 station 模式连家庭路由器**，Mac 留在家网 —— 稳定、可反复、不打断会话。
2. 只有**专门测试热点安全性**时才切到 SoftAP，并且必须在同一脚本里原子完成"切换→取证→切回"。
3. 连接被拒时的排查顺序：
   `networksetup -removepreferredwirelessnetwork`（清失效 profile）
   → 射频 off/on → 确认手机 Wi-Fi+蓝牙都关 → 最后才怀疑相机 AP 状态。
4. 后台任务一律用 `./s5ctl.sh start|stop|status` 管理，避免脚本失控。

## 4.5 两个被**证伪**的假设（记录以免重复踩）

### 4.5.1「BLE 握手会唤醒相机热点」——❌ 证伪

观察：一次实验中，执行 BLE 握手期间扫描到开放网络出现在 `t+25s`，一度以为相机是被握手"唤醒"了。

**反证**：后续用正确顺序（先 BLE 握手 → 等热点 → 再连接）复测，
`networksetup -setairportnetwork en0 "S5-XXXXXX"` 连续返回 **`Could not find network S5-XXXXXX`**
—— 说明**相机的 AP 根本没有起来**，之前扫到的开放网络是**别人的**。

### 4.5.2「扫到开放网络 = 相机热点」——❌ 不可靠

周边存在**多个开放网络**（信道 1/5/6/10 都出现过）。仅凭"有开放网络"判断相机热点在线，
会得到**假阳性**。可靠的判据只有两个：

1. `networksetup -setairportnetwork en0 "S5-XXXXXX"` **不报 `Could not find network`**；
2. 或连上后拿到 **`192.168.54.x`** 的地址。

⇒ 后续脚本里的"等热点出现"判据必须改成**按 SSID 试连**，而不是扫描开放网络。

### 4.5.3 相机端状态（用户实测）

- 相机进入**蓝牙配对模式**后：**Wi-Fi 关闭**（既非 station 也无 AP），BLE 正常广播。
- 相机屏幕**持续显示"等待配对"** —— 说明在相机看来**配对并未完成**；
  即：**BLE 侧握手成功（身份写入 + 读凭据）≠ 相机认为已配对**。
- 推测注册的完成还需要 **Wi-Fi 侧 accctrl** 那一步，而该步要求 **AP 在线**（AP 未起 → 无法完成）。

## 4.6 ✅ **机制确认：BLE 全程保持 → 相机自动开热点 → 可连上**（2026-10-13 07:53）

用户实测要点：**"先与相机握手之后它会自动开启 WiFi，而在配对模式下是无法退出的"**。

据此改成 **BLE 全程保持（`ble_hold`）+ 同时连热点**，一次即通：

```
[1] BLE 握手完成 t+17s（写身份 → 读 INITIAL_INFORM/SSID/密码 → 写就绪标记 → 保持连接）
[2] 收到标记立刻连热点 → ip=192.168.54.10  gw=192.168.54.1    ✅ 连上了
[3] accctrl：
    基线 req_acc → ok_under_research,S5-XXXXXX,remote,open
    req_acc(同UUID) → err_others_requesting,S5-XXXXXX,remote,open   ← 新状态
    轮询 +0s → err_user_refused      +3s → ok_under_research
[4] getstate/getinfo×4/getsetting/startsenddata → 全部 err_critical    ❌ 门仍未开
```

**结论**：
- **"先 BLE 后连热点、且 BLE 不能断"是正确时序** —— 之前所有 `-3970` / `Could not find network`
  都是因为热点尚未被唤起或已随 BLE 断开而关闭。
- 新增的 `err_others_requesting` 说明相机**能把 Wi-Fi 侧的请求与已注册的 BLE 身份关联起来**
  （否则不会说"已有其它设备在请求"），但**仍不放行** → **注册要完成还需要机身侧动作**。
- 相机随后报"连接失败"并**自动退出配对模式**。

### 4.6.1 本轮的自身缺陷（已修）

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | 保活定时器在**每次读到密码时都新建**一个 → 变成读循环轰炸 | 相机 13 秒后断开，屏幕上显示"连接失败"（很可能是被刷崩的） | 定时器**全局只建一次**；级联读只在首次握手时发生 |
| 2 | 把 `ok_under_research` 误判为"已授权" | 轮询逻辑提前结束，判断失真 | 只有**裸 `ok`**（不含 `under_research`/`err_`）才算授权 |

### 4.6.2 新发现：60606 是相机的 UPnP/DLNA 设备描述服务

```
http://192.168.54.1:60606/Lumix/Server0/ddd
  → 200  <?xml version="1.0"?><root xmlns="urn:schemas-upnp-org:device-1-0"
           xmlns:pana="urn:schemas-panasonic-com:pana">…
http://192.168.54.1:60606/            → 404
PORT /Lumix/Server0/ddd               → 403
50001                                 → 连接被 reset（非 HTTP 协议）
```

⇒ 热点模式下 `60606` 跑的是 **Panasonic 私有 UPnP 设备描述**（`/Lumix/Server0/`），
`50001` 是二进制协议且拒绝 HTTP。这两条在家网（station）侧**不存在**，属热点专属面。

## 4.7 名字对齐后的复测：不再锁死，但仍 `err_user_refused`（2026-08:00）

修掉两个自身缺陷（保活刷屏、授权误判）并把 **BLE 注册名与 accctrl `value2` 统一为 `MacBLE`**
后复测：

```
[ble] t+15s 握手完成；保活每 10s 一次 SSID 读（无刷屏）      ✅ 修好了
[ap]  ip=192.168.54.10 gw=192.168.54.1                     ✅ 连上热点
[3] req_acc  → err_others_requesting,S5-XXXXXX,remote,open
[4] +0s     → err_user_refused,S5-XXXXXX,remote,open         → 判为"用户拒绝"
    （脚本按设计立即停止轮询）
```

**改善**：本轮**没有再出现** `An invalid login occurred`（上一轮会锁死并要求断电）——
说明名字对齐确实消除了"无效登录"判定。

**未解决**：`err_user_refused` 依旧。相机**始终没有在机身上弹出确认提示**供用户点"允许"。

### 4.7.1 当前领先假设：相机要求 **BLE 层已绑定(bonded)** 才肯放行

综合全部实验，`err_user_refused` 的最合理解释是：

> 相机只在**请求方已完成 BLE 绑定（bonding）**时，才\(a\) 在机身弹出授权确认，或 \(b\) 直接放行。
> 我们全程是**未绑定的 BLE 连接**（`ble_diag` 证实：未绑定链路上任何裸读都会被 immediately 断链，
> 必须先按 App 顺序写身份才能读）——**协议顺序骗过了读，但骗不过配对状态**。

佐证：
- APK 里**没有任何 `createBond()` 调用**（`grep` 结果为 0），说明绑定由**操作系统**在收到
  "需要认证"时自动完成 —— Android/WinRT 都会自动绑定，而 **macOS CoreBluetooth 不会**
  （相机的回应是**直接断链**而不是回 `Insufficient Authentication`，macOS 因此不触发配对）。
- Windows 侧报告早已指出：**WinRT 有独立的绑定路径 `DeviceInformation.Pairing`，正是 macOS 缺的能力。**

⇒ **最后一块拼图很可能只能由 Windows/WinRT 侧补齐**（`04_工具与脚本/ble_win/s5_ble_pair.ps1`）。
