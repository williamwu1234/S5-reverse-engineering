# DC-S5 服务态 USB 通道勘察 —— 交接总结

**日期**：2026-10-14 · **交接人**：S5 逆向组 · **状态**：已完整刻画，未打通
**承接人需要做的**：见 §6（**大部分工作换到 Linux/Windows 做会容易得多**）

---

## 1. 为什么做这件事

起因是 SIGMA fp 的 **fpSup** 项目（<https://fpsup.ijigen.xyz>）：那台相机出厂自带一个
**77 条指令的工厂 shell**，开机时无条件执行 SD 卡根目录的脚本，作者据此实现了任意内存
读写，全部在 RAM、不刷固件。

我们的目标是看这条思路能否用在 S5 上。

**静态排查结论（已做完，见 §5.1）**：S5 固件 48 个分区里 **42 个是熵 8.0 的密文**，
唯一明文的 `loader1` 只是 UPD 容器头 + 分区表，**没有任何代码**；OSPO 公开的内核源码里
**没有**工厂 shell、没有 autorun。⇒ **fpSup 的机制无法静态验证，最可能待的地方是加密段。**

于是转向动态：**S5 在服务态会切换出一个私有 USB 个性，那是最接近"工厂通道"的东西。**

## 2. 一句话现状

> **服务态 USB 个性 `04da:2370` 已被完整刻画（描述符、端点、字符串、配置），
> 但在三个方向上都打不通：EP0 厂商 IN 全 STALL、bulk OUT 八种帧格式全被 NAK、
> 两个 IN 端点全程静默。它很可能属于松下的服务软件（非公开），而不是 LUMIX Tether。**

## 3. 已确认的事实

### 3.1 设备描述符（实测）

```
bcdUSB             = 0x0200
bDeviceClass/Sub/Proto = 0x00 / 0x00 / 0x00
bMaxPacketSize0    = 64
idVendor           = 0x04da  (Panasonic)
idProduct          = 0x2370
bcdDevice          = 0x0100
iManufacturer      = 1   "Panasonic"
iProduct           = 2   "DC-S5"
iSerialNumber      = 0        ← 标准序列号字段为空
bNumConfigurations = 2
```

**字符串索引 3**（设备描述符未引用，厂商自定义）是机身 ID：`0000000000000000000XJL2104270015`
—— 与 ROM BACKUP 导出的 ADJUST 区 `0x0000` 完全一致。
⚠️ **对外分发本包前必须脱敏这一串。**

### 3.2 两个配置：只差供电，接口与端点逐字节相同

| | 配置 0 | 配置 1 |
|---|---|---|
| `bConfigurationValue` | 1 | 2 |
| `bmAttributes` | `0x80` 总线供电 | `0xC0` 自供电 |
| `bMaxPower` | 250 = **500 mA** | 1 = **2 mA** |
| 接口/端点 | 完全相同 | 完全相同 |

**⇒ "第二个配置藏着固件更新接口"这一猜测已排除。**

### 3.3 接口与端点

```
Interface 0, alt 0, class 0xFF / 0xA0 / 0xB0 (vendor specific), 3 endpoints
  EP 0x01  OUT  bulk       mps 512  interval 0
  EP 0x82  IN   bulk       mps 512  interval 0
  EP 0x83  IN   interrupt  mps 64   interval 16
```

**第 3 个端点是 interrupt IN** —— 这是本次新发现。它说明该通道是
**「命令/响应 + 异步事件」架构**，不是只写的固件上传汇点。

> **为什么以前没发现**：`s5_ptp_raw.c:131` 写的是
> `if (tt != kUSBBulk) continue;` —— 在检查 interrupt 之前就把非 bulk 端点跳过了，
> 所以 `g_pipe_int_candidate` 永远是 0。**同样的 off-by-one 还出现在配置索引上**
> （`for (cfg = 1; ...)`，而 USB 的配置索引是从 0 开始的）。
> 两个 bug 都已在本包工具里修正。

### 3.4 PID 地图（三种个性）

| PID | 身份 | 证据 |
|---|---|---|
| **`0x2382`** | 正常 PTP / PC 模式 | 项目 `s5_ptp_dump` 成功 dump 65,545 B；**LUMIX Tether 的 `ConnectDevType=0`** |
| **`0x2370`** | 服务态 / `!→LUMIX` 触发的"等待主机"态 | 本次全部实测（对焦灯闪烁） |
| `0x2374` | **DMC-FZ28（2008 便携机）**，与本机无关 | gphoto-devel 邮件列表；Tether 的 `ConnectDevType=1` |

> ⚠️ **更正记录**：我曾据 Tether 反汇编推断"`0x2374` 是 S5 的目标模式"，**这是错的**，
> 已在上面更正。Tether 里类型 1 分支是**老机型兼容路径**（不带 `/PTPRemote/Server0/ddd`
> 驱动路径，也印证这点）。

## 4. 已排除的路径（含证据，不要再走）

| 路径 | 做法 | 结果 |
|---|---|---|
| **EP0 厂商 IN 请求** | 3 个接收者（`0xC0`/`C1`/`C2`）× `bRequest` `0x00–0xFF` × **6 个 `wValue`**（`0/1/2/0x100/0x8000/0xFFFF`），约 **4933 个请求** | **全部 STALL，0 命中**。每次实验前的 sanity check（标准 `GET_DESCRIPTOR`）均返回 18 字节 ⇒ **EP0 通路本身完好，是设备不应答** |
| **EP0 厂商 OUT 请求**（**零长度**，无数据阶段） | 3 个接收者（`0x40`/`41`/`42`）× `bRequest` `0x00–0xFF`，768 个请求 | **全部 STALL，0 命中**。`wLength=0`/`pData=NULL` 硬编码，无法携带载荷 |
| ~~EP0 类请求~~ | `0xA1`（IN class interface，PTP 用的方向） | 在 `0x2382` 上亦 0 命中 ⇒ **设备不实现类请求** |
| **bulk OUT 帧格式** | 8 种候选：PTP OpenSession(0x1002)、PTP GetDeviceInfo(0x1001)、PTP 形 opcode 0、ASCII `help\r\n`、ASCII `\r\n`、单字节 `0x00`、4 字节 LE 长度 0、16 个零字节 | **全部 `0xe0004051`（事务超时）= 设备 NAK，不接收** |
| **bulk IN / interrupt IN** | 被动监听 20 s 与 30 s（进 `!→LUMIX` 态前后各一次） | **0 字节**。interrupt interval=16，高速下周期约 4.1 s，30 s ≈ 7 个轮询周期仍无数据 ⇒ **设备确实不主动推事件** |
| **`SetConfiguration`** | 强制切配置 1、配置 2 | 配置 1 设置成功但**写入仍超时**；配置 2 设置失败 `0xe00002ed`。`GetConfiguration` 始终返回 `0xe00002ed`、值 0 ⇒ **配置切换不是关键** |

### 4.1 方法学验证（**重要，结论可信的前提**）

上述 0 命中结论的可信度建立在一组对照实验上（在**已知能应答的正常模式 `0x2382`** 上做）：

| 对照 | 结果 | 说明 |
|---|---|---|
| `SET_CONFIGURATION(1)`（与当前配置相同） | ✅ **ACCEPTED (0x0)** | **证明 OUT 通路与工具都能正确识别成功** |
| 厂商 OUT `0x40` × `0x01–0x40` | 全 STALL | 基线 |
| `SET_INTERFACE(1)` | STALL | 设备对冗余 SET_INTERFACE 也 STALL |
| `CLEAR_FEATURE(DEVICE_REMOTE_WAKEUP)` | STALL | **正确**——描述符 `bmAttributes` 未置 remote-wakeup 位 |

### 4.2 ⚠️ 一个必须写在前面的大坑

**`0xe00002ed` = `kIOReturnNotResponding` 就是 macOS 报告「设备 STALL」的方式**，
而不是 `kIOUSBPipeStalled`。

第一版 `s5_usb_ep0out` 把 `0xe00002ed` 当成"命中"，
**导致它在第一个请求就停下、厂商 OUT 扫描从未真正执行，却报告 `non-STALL=1`**。
这是典型的假阳性。修复后与 `s5_usb_ep0` 统一了判据。

**任何 STALL 判据必须包含**：

```c
kIOUSBPipeStalled | kIOReturnNotResponding(0xe00002ed) |
0xe0004051        | kIOReturnTimeout
```

### 4.3 附带发现：两种个性的接口类定义不同

| | 接口 class/sub/proto | EP83 interval |
|---|---|---|
| `0x2382`（正常） | **`0x06/0x01/0x01`** = 标准 PTP（Still Image） | 8 |
| `0x2370`（服务态） | **`0xFF/0xA0/0xB0`** = 厂商类 | 16 |

**不只是 PID 不同，整套接口定义都换了。**

## 5. 两个未解异常（值得承接人注意）

### 5.1 历史记录与本次实测矛盾

`13_服务模式与ROMBACKUP_20261013.md` §9 记录：

> 「发 PTP 命令（bulk OUT）→ ✅ **写入成功（设备 ACK 了数据）**」

而本次在**同一 PID、同一相机状态**下实测**全部超时**（`0xe0004051`）。

**两种可能**：
1. 当时相机停在某个特定服务页面，通道是活的；现在停在别处，通道睡着
2. 当时的日志判读有误

**若是第 1 种，那本身就是重大线索** —— 意味着通道活性取决于相机 UI 状态。
**建议承接人优先复核这一点**（见 §6 任务 4）。

### 5.2 `!→LUMIX` 是本次新发现的状态

`27_ROM_BACKUP导出成功与数据解析_20261013.md` §2 把 ROM BACKUP 菜单里的 `!→LUMIX`
标为"未知"。

**实测**：在 ROM BACKUP 菜单里执行该项后，**相机对焦灯开始闪烁**（"等待主机"信号），
USB 保持 `04da:2370`。

**这个闪烁灯是有用的状态指示器** —— 以后可凭它判断"是否处于等待主机态"。

**但要注意**：进入该状态后三个方向依然全死，说明它不是"等 Tether"，而更可能是
**等松下的服务软件**（非公开）。

> macOS 的 IOUSBLib 只能做已实现的操作；USB 抓包要手动 `ifconfig XHC20 up`

### 任务 1（零风险，优先级最高）：用 LUMIX Tether 抓包，拿到官方协议

**思路**：不要再猜帧格式 —— **让松下自己的软件去说话，我们在旁边录下来。**

- **Tether 认 `0x2382`**（`ConnectDevType=0`），而 **S5 正常模式正是 `0x2382`**
  ⇒ **Tether 本来就支持 S5，走正常模式，不是 `0x2370`**
- Tether 官网免费下载：
  <https://av.jpn.support.panasonic.com/support/software/lumixtether/download/d_lumixtether2.html>
- **抓包**：
  - Windows：**USBPcap + Wireshark**（推荐，最省事）
  - Linux：`usbmon` + Wireshark，或 `modprobe usbmon` 后 `tcpdump -i usbmon1`
  - macOS（不推荐）：`sudo ifconfig XHC20 up` 后 `sudo tcpdump -i XHC20 -w usb.pcap`
- **产出**：完整厂商协议帧格式，含 `adp_LMX_func_api_*` 系列（实时取景、设置、**固件更新**）

> **诚实提示**：Tether 是**消费级遥控软件**，它的协议大概率**不会直接给出 root 或明文固件**。
> 但它是松下官方协议，有 16 MB 带符号反汇编做对照，是目前最确定的收获。

## 7. 安全红线（务必遵守）

- **本包三个工具中，`s5_usb_desc` 与 `s5_usb_ep0` 是纯只读的**
  （`s5_usb_ep0` 代码里断言了方向位，无法写入）
- `s5_usb_listen` 默认**被动只读**；只有显式加 `--ptp` / `--tryall` / `--hex` 才会写入
- **服务菜单里除 `DSC→SD`（导出）外一律不碰**
  —— `SD*→DSC`（写回）、`ADJFLAG→ALL F`、`WBADJ→STEPMODE` 都可能造成**不可逆**后果
- **绝不真刷固件**
- 退出服务模式：按住 **`AF ON` + `方向右键`** 关机
- 异常时拔电池 10 秒
