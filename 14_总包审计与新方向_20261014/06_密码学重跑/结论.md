## 1. 单一真源 `upd_table.py`

新建 `upd_table.py`（**新文件，原脚本一律未改**），把偏移模型收敛成唯一入口：

```python
DATA_BASE = 0x200    # ★ doff 是相对它的偏移，abs_off = doff + 0x200
TABLE_BASE = 0x2EC   # 条目表起点
STRIDE = 92          # 每条 92 字节
COUNT_OFF = 0x2E8    # 条目数字段（运行时读取，不硬编码 48；带 0<n<=512 兜底 → 48）

entries(raw) -> [{idx, name, doff, size, addr, type, abs_off, sha, iv, ...}, ...]
data(raw, e) -> raw[e.abs_off : e.abs_off + e.size]          # ★ 唯一取数入口
data_legacy_wrong(raw, e) -> raw[e.doff : e.doff + e.size]   # 仅供"错误偏移对照臂"
self_test(raw) -> 命中数                                     # type=2 的 sha256(data)==记录sha
```

设计要点：
- **`abs_off` 只在 `entries()` 里算一次**，其他任何脚本都不允许再手写 `raw[off:]`；
- 「错误偏移臂」必须显式调用 `data_legacy_wrong()`，使对照结果**可审计、可复现**，不会与正确偏移混淆；
- `self_test` 是**闸门**：不到 7/7 就 `assert` 停止，不允许继续跑大规模穷举。

## 2. 实验 1：记录 SHA 的语义

**项目原结论**（`S5_AES破解可行性评估_20261011.md:116-121`，脚本 `verify_sha.py`）：
> 「记录 SHA 是逻辑校验和、≠ 存储字节哈希」

| 取偏移方式 | type=2 明文分区命中 | type=3 加密分区命中 | 全部 48 条 |
|---|---|---|---|
| **错误偏移** `raw[doff:+size]`（项目现状） | **2 / 7** | 0 / 41 | 2 / 48 |
| **正确偏移** `raw[doff+0x200:+size]` | **7 / 7 ✅** | 0 / 41 | 7 / 48 |

错误偏移下那 2 个「侥幸命中」也解释清楚了：
- `storage`（`size=0`）——空分区，任何偏移都命中；
- `lens_hist`（`size=0x60000`）——其内容**全部为 0x00**，平移 512 B 后仍全零，故两种读法都命中。

**旁证（与偏移无关的元数据）**：
- `storage` 的记录 SHA = `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` = **`SHA256(b'')`**；
- 3 组记录 SHA 完全相同的分区：`eep_ow_a`≡`eep_ow_b`、`eep_act_a`≡`eep_act_b`、`history`≡`ipu_data`。

**结论：❌ 推翻。** 记录 SHA **就是该分区【明文内容】的 SHA-256**。
- 对 type=2：直接 7/7 命中（明文即存储字节）；
- 对 type=3：字段存的是**加密前明文**的哈希 —— 这是**推断**，依据是同字段同结构 + 空分区退化 + `ipu_data` 的记录 SHA 与已验证的 `history` 内容哈希完全相同。
- **新能力**：该字段因此可用于**无密钥判定"两个分区明文是否相同 / 跨版本明文是否变化"**（本报告实验 2、3 都用到）。

### 3.3 keystream：错误偏移 vs 正确偏移

| 量 | 错误偏移（项目现状） | 正确偏移 |
|---|---|---|
| 明文非零字节 | 508 | **0** |
| 密文熵 | 7.9993 | 7.9993 |
| `ks = ct ⊕ pt` 熵 | 7.9993 | 7.9993 |
| `ks` 16B 自周期率 | 0.0041 | 0.0041 |
| `ct` 与 `ks` 是否逐字节相同 | False | **True**（明文全零 ⇒ 密文本身就是 keystream） |

两臂关系：`ks_wrong[i] == ks_correct[i-0x200]` 成立率 = **100.0000%**。
即项目手里的「256KB keystream」是**真 keystream 整体平移 512 字节的版本**：
其中 **99.80%** 的字节逐个都是**正确的 keystream 值**，只是位置错了 512 B；首/尾各 512 B 不属于真区间。

**结论：◐ 数值维持、语义修正。**
- 「熵 7.999 ⇒ 真加密流、无固定周期」**维持**（正确偏移下数值完全一致：7.9993 / 0.0041）；
- 但把它叫 **`keystream`** 是**术语错误**：只有 CTR/流式下 `ct⊕pt` 才等于 keystream，而模式**未判定**（见 3.4）；
- 已知明文为**全零** ⇒ 就 keystream 而言，**已知明文的信息量为 0**（`ks = ct`，没有任何额外信息）。

### 3.4 加密模式判决：CBC 还是流式？

**先纠正一条准则。** 任务书写道「若为 CBC 且明文全零 ⇒ 所有 16 字节密文块必须相同」——
**这在密码学上是错的**：

| 模式 | 全零明文下的密文 | 块是否全同 |
|---|---|---|
| **ECB** | `C_i = E_K(0)` | **全部相同** ← 这才是"块全同"的含义 |
| **CBC** | `C_0 = E_K(IV)`，`C_i = E_K(C_{i-1})`（迭代加密链） | **基本全不同** |
| **CTR/流式** | `C_i = KS_i` | **全不同** |

用**已知真模式**的自造样本实测（`out/04_exp4_positive_control.txt` 附 2）：

```
已知真模式 = CBC  明文=全零  →  块数=256  len(set(blocks))=256  所有块相同=False
已知真模式 = CTR  明文=全零  →  块数=256  len(set(blocks))=256  所有块相同=False
已知真模式 = ECB  明文=全零  →  块数=256  len(set(blocks))=1    所有块相同=True
```

**真·CBC + 全零明文，块全部互不相同** —— 该准则方向相反，据此**不能**判定 CBC。

**`ipu_data` 实测**（明文 = 全零，已证）：

| 读法 | 块数 | `len(set(blocks))` | 唯一率 |
|---|---|---|---|
| 错误偏移 | 16384 | 16384 | 100.00% |
| **正确偏移** | 16384 | **16384** | **100.00%** |

**⇒ 只能排除「ECB + 常量明文」，不能区分 CBC 与 CTR。**

**真正有判别力的对照：同明文 + 不同 IV**（这一对的「同明文」现在是**已证**的：记录 SHA 完全相同 + 记录 SHA 语义已由 7/7 确证）

| 对照对 | 记录SHA相同 | IV相同 | 逐字节相等率（正确偏移） | 密文完全相同 | XOR 熵 |
|---|---|---|---|---|---|
| `eep_ow_a` / `eep_ow_b` | ✅ | ❌ | **0.3716%** | ❌ | 7.9987 |
| `eep_act_a` / `eep_act_b` | ✅ | ❌ | **0.2930%** | ❌ | 7.9184 |

- ECB ⇒ 相等率应 **100%**（实测 ≈0.37% ⇒ **排除**）
- 固定 XOR 流（Nikon 式）⇒ XOR 应恒为 **0**（实测 XOR 熵 ≈8 ⇒ **排除**）
- CBC/CTR + 随机 IV ⇒ 相等率 ≈ **1/256 = 0.3906%**、XOR 熵 ≈8 ⇒ **与实测一致**

另：41 个 type=3 分区的 `size` **全部是 16 的倍数**（与分组密码一致；但 CTR 同样可选 16 倍长度，**不构成判决**）。

**结论：◐ 需进一步实验。** `ipu_data` 是 **CBC 还是 CTR，在本数据上不可区分**。
项目把它命名为「keystream」是术语越界；「AES-CBC/CTR 模式未定」这一自认**维持**。
要判定还需要：密钥本身、或同一 (key, IV) 下**明文被改动过**的第二份密文、或运行时 DDR 明文。

### 4.3 一个必须指出的过度解读（◐）

项目把跨版本结果读成「**固定密钥 + 逐构建随机 IV**」「密钥跨版本相同」。重算后：

- 48 个分区里，**「明文相同 **且** IV 相同」的只有 7 个，而这 7 个全是 type=2 明文分区**（IV 全零、根本没有加密）。
- **type=3 加密分区中，「明文相同 + IV 相同」的对照组 = 0 个**（41 个 IV 逐版本全变）。
- 因此跨版本数据对「密钥是否跨版本相同」**零检验力**：`明文同 + IV 不同 + 密文不同` 与
  「同密钥不同 IV」和「不同密钥」**都相容**，无法区分。

**⇒ ◐ 需进一步实验**：「固定密钥」目前只是**假设**，不是由跨版本实测支持的结论。

### 4.4 附：5 版 IV 稳定性

`IV 逐版本全变 41 个 / 全同 7 个 / 部分变化 0 个`（全同的 7 个正是 IV 全零的 type=2 分区）。
**项目「41 个 IV 逐版本全变、全唯一、不可由 name/index/model 派生」✅ 维持**——
IV 是**元数据**，不受 `+0x200` 修正影响。

### 4.5 修正的副产品：错误偏移会**制造假的相似性信号**

小分区上错误偏移的影响不是"略偏"，而是**量级错误**：

| 分区 | 错误偏移相等率 | 正确偏移相等率 | 倍数 |
|---|---|---|---|
| `loader1` | **12.3291%** | 0.2930% | **42×** |
| `zboot` | **25.0977%** | 0.1465% | **171×** |
| `koutei_kao` | 0.8414% | 0.3976% | 2.1× |

一个只看小分区的分析者，用错误偏移会看到 ~12–25% 的「跨版本密文相同」，从而**错误地**得出
「存在版本稳定 keystream」的结论。这是一条独立的、可复用的风险提示。

## 5. 实验 4 ★：阳性对照 —— 证明"0 命中"是**假阴性**

**问题**：真实固件里我们不知道密钥，所以**无法**从"0 命中"本身判断搜索逻辑有没有检验力。
必须自造「已知密钥 + 已知明文」样本做**阳性对照**。

**对照设计**（`exp4_positive_control.py`）：
- 容器结构镜像真实 UPD：表在 `0x2EC`、条目 92 B、`doff` 相对 `0x200`、真密钥藏在表头 `0x100`；
- 搜索逻辑照抄 `keyhunt.py` / `keyhunt2.py`：候选 = 表头 16/24/32 B 窗口 + sha256/md5/sha1 派生 + 填充 → **5240 个**（另跑 **211** 子集）；IV = 表内 IV / 全零 IV / 表头 IV（= "3 IV"）；模式 = CBC/CTR/ECB；密钥长度 16/24/32；
- 两套 oracle：`Oracle-SHA`（`sha256(decrypt(ct)) == 记录SHA`，keyhunt.py 口径）、`Oracle-PREFIX`（`decrypt(ct[:64]) == 明文[:64]`，keyhunt2.py 口径）；
- **唯一变量 = 读 `ct`/`pt` 的偏移**。

**自检（这一步让对照有效）**：
```
[对照集合自检] 候选密钥数 = 5240；真密钥是否在候选集合中 = True (来源: ['hdr@0x100/len16'])
```
⇒ 正确密钥**确确实实在被测集合里**，所以"没找到"只可能是**搜索逻辑的问题**。

**结果矩阵**（各 6 种配置：{随机结构明文, 常量全零明文} × {CBC, CTR, ECB}）：

| 口径 | 错误偏移 | 正确偏移 |
|---|---|---|
| Oracle-SHA | **6/6 全部漏检（假阴性）** | **6/6 全部命中真密钥**（各 1 个不同密钥，无假阳性） |
| Oracle-PREFIX | **6/6 全部漏检（假阴性）** | **6/6 全部命中真密钥** |

**211 子集口径**（对应项目「211 候选真实 AES 恢复」）：
```
子集大小 = 211，真密钥在集合中 = True
  wrong 偏移: 命中 0 个
correct 偏移: 命中 6 个（含正确密钥: 00112233445566778899aabbccddeeff / CBC）
```

**诊断：用【已知的正确密钥】在两臂各解一次**（节选）

| 明文 | 模式 | 臂 | 解密结果 SHA[:16] | 记录 SHA[:16] | 相等 |
|---|---|---|---|---|---|
| 随机结构 | CBC | 正确 | `f30d8ad31a99b872` | `f30d8ad31a99b872` | **True** |
| 随机结构 | CBC | **错误** | `b0f703517ba9c814` | `f30d8ad31a99b872` | **False** |
| 常量全零 | CTR | 正确 | `ad7facb2586fc6e9` | `ad7facb2586fc6e9` | **True** |
| 常量全零 | CTR | **错误** | `d769db237bdcb784` | `ad7facb2586fc6e9` | **False** |
| 常量全零 | ECB | 正确 | `ad7facb2586fc6e9` | `ad7facb2586fc6e9` | **True** |
| 常量全零 | ECB | **错误** | `045c272783c66fed` | `ad7facb2586fc6e9` | **False** |

> `ad7facb2586fc6e9…` 正是 `SHA256(全零)`，可独立核对。

**★ 阳性对照成功。结论：**

1. `keyhunt.py` / `keyhunt2.py` 那两次「0 命中」**对假设零检验力** —— 即使**正确密钥就在候选集合里**，
   错误偏移也会 100% 漏检（CBC/CTR/ECB、两套 oracle、两种明文，**12/12 配置全部漏检**）。
2. 机理：错误偏移把密文整体错开 **512 B = 32 个 AES 块**，`E_K` 的输入块全错 ⇒ 解密结果是**垃圾**，
   与真明文毫无关系（见诊断表）。
3. 因此 **「5240 key × 3 IV = 0 命中」与「211 候选 = 0 命中」不能支持「密钥不是文件内派生的」** —— 
   **❌ 推翻**这两条推论。
4. 反过来，**修正后的搜索逻辑是有效的**（正确偏移 6/6 命中真密钥、且只命中真密钥），
   所以「用正确偏移重跑搜索」这件事**值得做**——它现在是一次有检验力的实验。
