## 三、实机新发现（项目未记录）

### ③-1 ★★★ 60606 在 **station（家网）模式**即暴露，且**无需认证**

项目 `18 号:89-94` 记录 `60606` 是**热点专属**面。实测：相机连在家网时该端口同样开放。

```
GET http://192.168.1.131:60606/Lumix/Server0/ddd  → 200 OK, 1624 B
```

内容是一份标准 **DLNA MediaServer（`M-DMS-1.50`）设备描述**，**无需任何认证**即可读取：

| 字段 | 值 | 性质 |
|---|---|---|
| `friendlyName` | `S5-XXXXXX` | 泄露设备名（= Wi-Fi MAC 后 6 位） |
| `modelNumber` | `DC-S5` | 机型 |
| **`serialNumber`** | **`WJ1DA004124`** | ★ **第二个机身序列号，全项目从未打码** |
| `UDN` | `uuid:4D454930-0100-1000-8000-707414XXXXXX` | ★ **明文嵌入 Wi-Fi MAC** |
| `pana:X_FirmVersion` | `2.90` | 与用户固件 `VD4.30` 不同（服务侧固件号） |
| `pana:X_PTPPortNo` | `15740` | PTP 端口 |
| `pana:X_AdditionalFunction` | `CPRemoteView` | 远程取景能力标志 |

**边界（已实测，很重要，避免夸大）**：两个 UPnP 服务（`ContentDirectory:1`、`ConnectionManager:1`）的**所有 SOAP 控制动作一律 `403`**，包括纯只读的 `GetProtocolInfo`、`GetSystemUpdateID`、`Browse`（直连与换 DLNA User-Agent 均 403）。
⇒ 该面的性质是 **信息泄露（information disclosure），不是文件访问**。不要把它写成"可读取 SD 卡"。

**端口对照**：`60606` 开放（200/404）、`50001` 在 station 模式**关闭**、`80` 返回 403。

**修复建议**：把 `WJ1DA004124` 纳入脱敏表；对外分享前须注意该端点可在同网段被任意主机读取。

### ③-2 ★★ 菜单 `enable` 的语义已判定：**"可选"，不是"当前"**

实测证据（当前 `videoformat=mov`、`ntsc_pal=ntsc`）：

```
menu_item_id_videoformat_mp4          enable="yes"     ← 与 mov 同时为 yes
menu_item_id_videoformat_mov          enable="yes"
menu_item_id_ntsc_pal_ntsc            enable="yes"     ← 与 pal 同时为 yes
menu_item_id_ntsc_pal_pal             enable="yes"
```

⇒ **`enable="yes"` =「该选项在当前模式下可被选择」**，而不是「当前生效值」。
**后果**：项目用 `curmenu` 的 `enable="yes"` 集合来数"可选档位"是**正确用法**；但不能用它判断当前值（当前值要靠 `getsetting`）。这一条此前未被明确写下，是复现者容易踩的坑。

### ③-3 ★★★ LUT 相关的实机结论（回答"能否给 S5 套 LUT"）

| 检查 | 结果 |
|---|---|
| `allmenu` / `curmenu` 中的 LUT 菜单项 | **0 个**（7 处 `lut` 命中全是 "High-Reso**lut**ion" 的多语言标题，误报） |
| `getinfo type=` 的 LUT 相关类型（`lut`/`ad_lut`/`vlt`/`vlog`/`viewassist`/`lutinfo`/`lutlist`…） | **全部 `err_param`** ⇒ 无此类型 |
| `capability` 中的 LUT 能力位 | **无**（`camspec` 17 项、`camcmd` 6 项，均无 LUT） |
| camsetting blob（65533 B）中的 LUT/VLT/cube 字样 | **0 处** |
| **V-Log 照片风格** | **`menu_item_id_ph_sty_vlog` = `enable="yes"`** ⇒ **V-Log 在本机可选**（`ph_sty_vlog_l` = no） |

**推论（待外部资料线程确认格式细节）**：
- DC-S5 的 **HTTP API 层完全没有 LUT 面**——不存在"通过 Wi-Fi 上传 LUT"的路径。
- 但 **V-Log 可选**是 **V-Log View Assist（LUT 查看助手）** 的前置条件。该功能是**机身菜单内的监看辅助**（LUT 从 SD 卡加载、只影响取景/显示、**不烧录进文件**）。
- ⇒ **在初代 S5 上"套 LUT"的正路是：机身菜单 → V-Log View Assist → 从 SD 卡加载合规 LUT 文件**；这是官方功能，不是破解。
- ⇒ **"实时 LUT（烧录进 JPEG/视频）"是 S5II/S5IIX/GH7/S9/S1M2 一代的能力**；DC-S5 无对应菜单项、无 API、无 blob 字段。若要在 S5 上实现类似效果，只能靠**后期套 LUT**。

> 待确认项（外部资料线程）：LUT 文件格式（`.VLT` vs `.cube`）、SD 卡目录名、网格尺寸/位深限制、初代 S5 是否确实不支持 `.cube`。**具体结论见 LUT 专题线程的回收结果。**

## 四、离线验证（零设备、零风险）

### ④-1 方向 15（S5 U-Boot console 离线核验）→ **结论：S5 上不可判定，但已排除"离线找得到"**

用**正确偏移 `+0x200`** 对全部 7 个 type=2 分区（共 2,490,368 字节，SHA 全部自检通过）搜索 U-Boot 环境变量痕迹：

```
BOOTDELAY / console= / loglevel / bootargs / bootcmd / baudrate / U-Boot / u-boot /
Das U-Boot / stdin= / stdout= / ENV_IS_NOWHERE / bootdelay / preboot / verify= / ipaddr / ethaddr
→ 命中 0
```

**并且发现**：这 7 个"明文分区"其实是 **OTA 容器里的空占位**，不是真实配置数据：

| 分区 | 填充 |
|---|---|
| `history`、`lens_hist`、`ninsho_db`、`wifi_info` | **全 `0x00`** |
| `fileinfo`、`menu_save` | **全 `0xFF`** |
| `storage` | size = 0 |

**结论**：
- `UART console 死路` **在 S5 上无法从离线证据判定**；项目此前仅凭 **S1R2 类比**（`06_S1R2:33-35`），而 `00_S5结合点:82` 自己也把该核验标为"未做"。
- 引用时必须写成 **"S5 未验证"**，不能写成"已排除"。要判定只能靠**拆机接 UART 读 bootlog**。
- 顺带：**OSPO 发布的 OSS 内核树不含 U-Boot 源码**（README 亦承认），所以离线路径本就不存在——这条现在有明确边界了。

### ④-2 方向 4（已知明文扩面）→ **结论：基本关闭**

对全部 **41 个加密分区**测试 **13 种均匀明文模板**（`0x00/FF/55/AA/0F/F0/01/7F/80/CC/33/5A/A5`）+ 4 种结构化模板（原存储前 512/1024/2048/4096 字节 + 全零）：

```
命中 1 个：ipu_data（262144 字节，明文 == 全零）
结构化模板命中 0 个
```

**并且严格证实了唯一已知明文对**：

```
ipu_data  (type=3, size=262144, IV=0e43dbd57c2da5fbc9c59ba5a71f9f37)
  记录 SHA       = 8a39d2abd3999ab73c34db2476849cddf303ce389b35826850f9a700589b4a90
  SHA256(262144 个 0x00) = 8a39d2abd3999ab73c34db2476849cddf303ce389b35826850f9a700589b4a90
  → 相等 ✅  ⇒ 明文确为全零（"记录 SHA = 明文 SHA"这一前提在此得到独立印证）
```

**结论**：**不存在更多已知明文**。想靠"多找已知明文"推进 AES 的路到此为止。
⇒ 这也意味着：任何 AES 验证器**只能依赖这一对**（256 KB 全零明文）。这是硬约束，后续所有密码学工作都必须在此前提下设计。

### ④-3 对"记录 SHA 语义"的补强

`+0x200` 正确偏移下：
- **type=2 分区：7/7 记录 SHA = 存储字节 SHA**（因为存储字节就是明文）✅
- **type=3 分区：记录 SHA = 明文 SHA**（由 ④-2 的 `ipu_data` 独立证明）✅

⇒ 项目的记录 SHA 字段语义（"明文的 SHA-256"）**成立**；而 `S5_AES…:116-121` 的"记录 SHA 是逻辑校验值、≠ 存储字节哈希"是 `verify_sha.py` 偏移 bug 的产物——**该结论已被正式推翻**。

### ⑧-1 勘误：我写的 CBC 判决准则是**错的**（已被线程实测纠正）

我在 [`03_新方向与实验设计.md`](14_总包审计与新方向_20261014/03_新方向与实验设计.md) 方向 5 里写过
「若为 CBC 且明文全零 ⇒ 所有 16 字节密文块必须相同」。**这是密码学错误**：

- **块全同**是 **ECB + 常量明文**的指纹；
- **CBC + 全零明文**是迭代链 `C_i = E_K(C_{i-1})`，块**基本全不同**。

`06_密码学重跑` 线程用自造样本实测：真 **CBC** + 全零 → `len(set(blocks)) = 256/256`；真 **ECB** + 全零 → `1`。
而 `ipu_data` 正确偏移下实测 `16384/16384` ⇒ **只能排除 ECB；CBC 与 CTR 在本数据上不可区分**。

**已修正**：[`03_新方向与实验设计.md`](14_总包审计与新方向_20261014/03_新方向与实验设计.md) 方向 5 已按上述重写并加勘误框。
**教训**：判据类准则在写进实验设计前应先做**阳性/阴性对照自测**——这正是本次 `exp4_positive_control.py` 起的作用。
