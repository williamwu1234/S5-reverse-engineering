#### S1 ★★★ 10-14"受控复测"的写入是**空操作**，持久化旗舰结论证据不成立

**现象**：报告 31 声称"写入 `ntsc + mov + 0x9b` 后断电重启三项均保留（T1/T2）"，并把 §3.2 称为"写入确已落地的验证"。但该报告 §7 自己列出的证据文件显示，**写入 payload 与写入前备份为同一份文件**。

```text
backup_pre_restore_20261014_175604.bin   sha256 dbaf409c95382710…
restore_payload_20261014_175604.bin      sha256 dbaf409c95382710…   ← 0 字节差异
backup_pre_restore_20261014_180310.bin   sha256 2d8c0a767c8c2306…
restore_payload_20261014_180310.bin      sha256 2d8c0a767c8c2306…   ← 0 字节差异
```
两个备份在**写入前**就已经是 `65230=0x00(ntsc)` / `3062=0x06(mov)` / `6986=0x9b`，槽形态也已是 `06 05×12`。

**为什么这是致命的**：
- 报告 §3.2 用**槽形态 `06 05×12`** 作为"写入已落地"的签名。但该形态在写入前的备份中**已经存在**，因此它对"是否写过"**零信息量**。
- 报告 §3.2 的判读注意（:87–90）自己写明"该形态不唯一对应上传写入……相机自身行为也可产生同一形态"，却在 :85 直接下结论"⇒ 可判定写入已落地"。**报告内部自相矛盾**。
- 由此：`31 §5 "三项均跨断电保留"` 只能读作"一个**原本就存在**的状态在重启后仍是它自己"，无法支撑"blob 写入可持久化"。
- 对照组仍未失效的部分：`restore_payload_20261014_015738.bin` 与备份**差 2 字节**（quality 0xc1→0x9b + 校验和），是**真实写入**。所以"mov 曾在 flash 中存活"未被否定，但**不是 T1/T2 造成的**。

**证据**：[31 号报告](01_研究报告/31_录制格式持久化_受控复测_20261014.md) §3.2/§5/§7；`04_工具与脚本/campaign2/out/{backup_pre_restore,restore_payload}_20261014_{175604,180310}.bin`

#### S2 ★★★ 固件密码学实验被 **off-by-0x200** 污染，"AES 终局否定"证据不足

**现象**：UPD 分区表条目中的 `doff` 是**相对数据基址 0x200 的相对偏移**，正确绝对偏移 = `doff + 0x200`。项目在 2026-10-14 的勘误 E1 中自己承认了这一点，但**只修了 `parse_upd.py` 一个文件**。

**审计方独立复算（R4）**：

| 取偏移方式 | 7 个 type=2（明文）分区记录 SHA 命中率 |
|---|---|
| `raw[doff+0x200 : +size]` | **7 / 7 ✅** |
| `raw[doff : +size]`（脚本现状） | **2 / 7 ❌** |

```bash
python3 - <<'PY'
import struct,hashlib
raw=open("02_固件二进制/DC-S5/S5___V29.bin","rb").read(); base=0x2EC
ok1=ok2=n=0
for i in range(48):
    off=base+i*92
    doff,dsize,daddr,dtype=struct.unpack_from("<IIII",raw,off+0x0C)
    if dtype!=2: continue
    sha=raw[off+0x1C:off+0x3C].hex(); n+=1
    ok1+= hashlib.sha256(raw[0x200+doff:0x200+doff+dsize]).hexdigest()==sha
    ok2+= hashlib.sha256(raw[doff:doff+dsize]).hexdigest()==sha
print(f"type=2 共{n}: +0x200 命中 {ok1}/{n}; 原值命中 {ok2}/{n}")
PY
# 预期输出：type=2 共7: +0x200 命中 7/7; 原值命中 2/7
```

**未修正的 7 个脚本**（仍用 `raw[doff:]`）：`keyhunt.py:16,38`、`keyhunt2.py:17-19`、`ks_extract.py:13-15`、`exp_cipher.py:27-28,42`、`verify_sha.py:27`、`xver_fixed.py:23`、`verify512.py:10`、`rawtest.py:38`、`xver2.py:44`

**为什么"偏一点"其实是致命的**：`keyhunt.py` / `keyhunt2.py` 的判定是"用候选密钥解密某段密文，再与明文比对"。由于**密文与明文用了同一个错误偏移**，即使正确密钥出现，它解密的也是**错位的 512 字节**，块对齐全乱 → 结果必为垃圾。**这两个"真实 AES 密钥恢复测试"对假设零检验力**，其"0 命中"不构成证据。

**连带失效的结论**：
| 主张 | 出处 | 状态 |
|---|---|---|
| 5240 key × 3 IV = 0 命中 | `S5_AES破解可行性评估_20261011.md:79` | ❌ 需重跑 |
| 211 候选真实 AES 恢复 = 0 命中 | 同上 :559-565 | ❌ 需重跑 |
| "256KB 真实 keystream" | 同上 :12,77 | ⚠️ `ks=ct⊕pt`，pt 全零 ⇒ ks 就是密文；仅 CTR 下才是 keystream |
| "记录 SHA ≠ 存储字节哈希" | 同上 :116-121 | ❌ 已被 R4 直接反证 |
| "130k+ 探测" | `00-总评估:85` | ⚠️ 实为 S1M2（MC8243）的 132,360 次试验，且原文自己声明"不是对密钥空间的穷举" |

**证据**：`01_研究报告/29_S1R2报告启示与S5对称密钥分析_20261014.md`（勘误 E1–E6）、`04_工具与脚本/firmware_crypto/`、`06_数据与证据/firmware_crypto_s5/pairs_s5.json.WRONG_offby0x200`（项目自己留下的错误版文件）

**结论定性**：站得住的只有"**密钥不在固件文件内**"这一负向结构观察 + "官方单一 .bin ⇒ 主密钥按机型固定"的商业逻辑推演。这支持"离线拿密钥希望渺茫"，**不支持"终局""已证实"**。项目自己在 `S5_AES…:416` 也写了"不是对密钥空间的穷举证明"——与摘要层"已证实（终局）"自相矛盾。

### ⚠️ 补充（2026-10-14 由 `07_签名与密钥恢复` 线程裁决）：签名类结论的前提**已被上游自我撤回**

| 项 | 核查结果 |
|---|---|
| 项目（及本表原先）把 `0x220` 的 64B 当作 **ECDSA P-256 签名**使用 | **证据链是三级转述**。其源头 `07_参考仓库/s1m2-research/docs/CORRECTIONS.md` **明文更正**：「外层 ECDSA 字段与签名机制**已经确认**」→「字段名称**是候选**；**没有签名验证和完整机制证据**」。该项目自己的 `siegfried82_notes.md:52` 也只写「**推断**为标准 ECDSA P-256」 |
| 该说法的原始依据 | 仅「长度 = 64 字节」 |
| **ECDSA 公钥恢复实测** | **90,144 组**假设（**602 个唯一消息候选** × 3 曲线 [P-256/secp256k1/brainpoolP256r1] × **11 种哈希** × 4 种编码端序），约 **1,014 GB** 哈希 → **0 收敛，公钥未恢复**。消息族含：任务指定 8 范围、签名区清零/整段移除、头部 `0x1C/0x24/0x3C/0x40` 全部 16 个子集清零、复合拼接、分区表内嵌 SHA-256、尾部锚定区间、**全部结构边界两两组成的连续区间穷尽扫描**。工具自检 **6/6 PASS**（真收敛必被检出；不同私钥阴性对照 0 误报；RSA 恢复 N 并用第 3 版独立验签通过）⇒ 这个"否定"是有意义的 |
| Ed25519 排他 | 5 版仅 1 版满足 `S<L`（随机期望 1/16）⇒ 不支持 |
| **RSA-4096 模数恢复** | e ∈ {3,5,7,17,257} × 3,620 候选 × BE/LE **全排除**；e=65537 前 24 名高先验候选（PKCS#1 v1.5 + DigestInfo）× BE/LE **全排除**（3,012 s）⇒ **未恢复出模数 N**；「尾块 512B 是 RSA-4096」**无正面依据**（512B=4096bit 只是尺寸巧合） |
| 两处推理更正 | ①「尾块首字节 `89 a1` 不是 `00 01`，故排除 PKCS#1 v1.5」**不成立**——`s = m^d mod N` 在 `[0,N)` 近似均匀，`00 01` 前缀描述的是**编码后的消息 m**，不是 `s`；②「`r,s ∈ [1,n-1]` 支持 P-256 判定」**几乎无信息量**——随机 256-bit 整数落在该区间的概率是 `1−2^−32` |
| **「版本字段在签名覆盖内」** | **裁决：不可判定**。**可数学确证（与签名方案无关，5/5 实测）**：`stored CRC32 == zlib.crc32(data[0x200:])`、内层头 `0x2A0-0x2E0` 逐字节等于外层头 `0x00-0x40`、`0x3C == L-0x200`。因此外层 `0x1C`/`0x24` **不在** CRC32 覆盖内；内层副本 `0x2BC`/`0x2C4` **在**覆盖内且落在 `[0x200, L-512)` ⇒ **只要存在任何覆盖 ⊇`[0x200, L-512)` 的签名，版本字段的值就被该签名覆盖**。可确证的只有 CRC32 部分（与签名方案无关）：外层 `0x1C`/`0x24` **不在** `crc32(data[0x200:])` 覆盖内；内层副本 `0x2BC`/`0x2C4` **在**覆盖内；内层头 `0x2A0-0x2E0` 逐字节等于外层 `0x00-0x40`。外层 `0x0-0x200` 是否被带密钥签名覆盖，**离线无法裁定**；而项目文档的具体假设「ECDSA 最可能覆盖外层头 `0x0-0x200`」**在穷举范围内已被排除** |

⇒ **应把 `verify_logic_notes.md` / `FIRMWARE_FORMAT.md` 中把 `0x220` 当事实使用的段落整体降级为「候选假设」**；
⇒ 文档里「改版本号必然破坏 ECDSA」应改为「**ECDSA 那一半没有正面证据**」；
⇒ 只改外层 `0x24`（不动内层副本与 CRC）是否会被检出，**离线不可判定**——这既不能支持"可以绕过"，也不能支持"必然被拒"。

**唯一能终结这个问题的路径（需容器外信息）**：拿到 BootROM/OTP 内的公钥后，把 `recover` 换成 `verify`（单次验签 <1 ms，消息空间可扩大几个数量级），或从 UART bootlog 看有无验签告警以确认验签是否 ENFORCING。

## 6. 两条应写入项目方法学铁律的建议

项目已有一条铁律（`REPO_CONTENTS.md:67-70`）：
> ① 没有对照组的结论不要写进报告；② "相机报写入错误"不能当作"内存写已执行"的判据。

本次审计证明这两条**不够**——因为 S1 的空操作、S2 的偏移 bug 都不是"缺对照组"，而是**实验/工具本身无效却未被检出**。建议补充：

> ```python

> if payload == cur:
>     log("!! payload == current readback: NO-OP write, experiment invalid. Aborting.")
>     sys.exit(2)
> ```

> **④ 任何依赖结构化二进制偏移的结论，必须附一个"偏移判决实验"：用已知明文/已知校验的和验证同一偏移模型在多个样本上命中，并在 `TOOLS.md` 登记单一真源（如 `upd_table.py`）。**
