**推荐做法：抽一个单一真源，而不是逐个打补丁**（避免再次分裂）：

```python
# 新建 upd_table.py —— 唯一的偏移/表结构真源
import struct
DATA_BASE = 0x200          # ★ 数据基址：所有 doff 都是相对它的
TABLE_BASE = 0x2EC         # 条目表起点
STRIDE = 92
COUNT_OFF = 0x2E8          # 条目数（不要硬编码 48）

def entries(raw):
    n = struct.unpack_from("<I", raw, COUNT_OFF)[0]
    if not (0 < n <= 512):      # 兜底
        n = 48
    out = []
    for i in range(n):
        off = TABLE_BASE + i*STRIDE
        if off + STRIDE > len(raw):
            break
        name = raw[off:off+12].rstrip(b'\0').decode('ascii', 'replace')
        doff, dsize, daddr, dtype = struct.unpack_from("<IIII", raw, off+0x0C)
        out.append(dict(
            idx=i, name=name, doff=doff, size=dsize, addr=daddr, type=dtype,
            abs_off=DATA_BASE + doff,          # ★ 唯一的绝对偏移定义
            sha=raw[off+0x1C:off+0x3C],
            iv=raw[off+0x3C:off+0x4C],
        ))
    return out

def data(raw, e):
    """取分区内容。永远用这个函数，不要手写 raw[off:]"""
    s = e["abs_off"]
    return raw[s:s + e["size"]]
```

然后把 7 个脚本里的 `raw[d['off']:]` 全部替换为 `upd_table.data(raw, d)`，并**先跑一次判决实验确认模型正确**：

### 方向 2 ★★★★★ ECDSA P-256 公钥恢复 —— 把"强假设"变结论

> **✅ 已完成（2026-10-14）。累计 90,144 组假设（602 唯一消息候选 × 3 曲线 × 11 哈希 × 4 编码端序，约 1,014 GB 哈希）→ 零收敛，公钥未恢复；工具自检 6/6 PASS 故该否定有意义。「版本字段是否在签名覆盖内」裁决为【不可判定】。**
> 详见 [`07_签名与密钥恢复/结论.md`](14_总包审计与新方向_20261014/07_签名与密钥恢复/结论.md)。
> **并且查出一件更重要的事**：项目把 `0x220` 当 ECDSA P-256 签名使用，但其**源头（S1M2 研究仓库 `docs/CORRECTIONS.md`）已自我撤回**该断言（「字段名称是候选；没有签名验证和完整机制证据」）。⇒ 该字段应整体降级为**候选假设**。

**为什么可行**
固件外层 `0x220` 处有 64 字节 ECDSA P-256 签名 `(r,s)`，5 个版本各一份。用标准**公钥恢复（public key recovery）**，配合可猜的消息摘要候选，可以反推出签名公钥；若同一公钥能满足全部 5 个版本，则公钥恢复成功。**这是纯离线大整数运算，零风险。**

**能回答的关键问题**
- 签名到底覆盖哪一段字节？（`data[0x200:]`？整文件？是否含 0x1C 版本字段？）
- 项目自认的"版本字段在签名覆盖内"（`verify_logic_notes.md:78-79`）是**强假设、未验签**——本方向可直接判定。
- 一旦拿到公钥，**改版本号绕过签名门**类的实验可以先在本地验签，不必冒真机风险。

**怎么做**

```bash
pip3 install ecdsa    # 轻量，纯 Python

cd "/Users/wuwilliam/Documents/ChatGPT/S5_逆向_项目总包_20261012"
python3 - <<'PY'
import hashlib, itertools, struct
from ecdsa import VerifyingKey, SECP256k1, NIST256p
from ecdsa.util import sigdecode_string

FW = {"V29":"02_固件二进制/DC-S5/S5___V29.bin",
      "V24":"02_固件二进制/DC-S5_版本历史/S5___V24.bin",
      "V23":"02_固件二进制/DC-S5_版本历史/S5___V23.bin",
      "V20":"02_固件二进制/DC-S5_版本历史/S5___V20.bin",
      "V11":"02_固件二进制/DC-S5_版本历史/S5___V11.bin"}

def sig(raw):
    return raw[0x220:0x260], raw[0x260:0x2A0]   # (r, s)；先按这个切法，必要时调整

# 候选摘要：不同覆盖范围 × 不同哈希
def digest_candidates(raw):
    yield "sha256(raw)",            hashlib.sha256(raw).digest()
    for start in (0x200, 0x2A0, 0x2E0, 0x142C):
        yield f"sha256(raw[{start:#x}:])", hashlib.sha256(raw[start:]).digest()
    # 去尾块（RSA-4096 = 512B）
    yield "sha256(raw[:-512])",     hashlib.sha256(raw[:-512]).digest()
    yield "sha256(raw[0x200:-512])",hashlib.sha256(raw[0x200:-512]).digest()

# 逐版本、逐候选，做公钥恢复；记录哪个 (range, hash) 对全部 5 版都给出同一公钥
from ecdsa import SigningKey
recovered = {}
for name, path in FW.items():
    raw = open(path,'rb').read()
    r, s = sig(raw)
    for label, dg in digest_candidates(raw):
        try:
            vk = VerifyingKey.from_public_key_recovery_with_digest(
                r, s, NIST256p, dg, sigdecode=sigdecode_string)
        except Exception:
            continue
        for cand in vk:
            key = cand.to_string().hex()
            recovered.setdefault((label, key), set()).add(name)

print("候选公钥 | 覆盖 5 版的组合：")
for (label, key), names in sorted(recovered.items(), key=lambda kv:-len(kv[1])):
    if len(names) >= 2:
        print(f"  {len(names)}/5  {label}  pub={key[:32]}…  ver={sorted(names)}")
print("\n（若出现 5/5 的组合，即为正确签名覆盖域与公钥）")
PY
```

**成功判据**：出现一个 `(覆盖范围, 哈希)` 组合，使 **5/5 版本**都恢复出**同一公钥**。
**失败也有收获**：若 5 版无法收敛到同一公钥，说明签名并非 P-256、或签名布局/端序与假设不同 ⇒ 直接修正 `FIRMWARE_FORMAT.md` 的字段定义。

**修复后再做**：用恢复出的公钥本地验签，测试"改 `0x1C` 版本字段后签名是否失效"——**这是在纸上完成、而非在相机上冒险**。

### 方向 3 ★★★★ RSA-4096 模数恢复

> **✅ 已完成（2026-10-14）**：e ∈ {3,5,7,17,257} × 3,620 候选**全部排除**；e=65537 前 24 名高先验候选（PKCS#1 v1.5 + DigestInfo）**也全部排除**。
> 结论：「尾块 512B 是 RSA-4096 签名」**无正面依据**（512B=4096bit 只是尺寸巧合）。

**为什么可行**
固件尾部有 512 字节 RSA-4096 签名区。若为**裸 RSA（无填充或无已知填充）**，用两组 `(sᵢ, mᵢ)` 可求
`N = gcd(s₁ᵉ − m₁, s₂ᵉ − m₂)`（`e` 常为 65537，也先试小 `e`）。
`verify_logic_notes.md:97-99` 已排除 PKCS#1 v1.5 ⇒ 疑为 PSS 或裸 RSA，正好适用。

**代价**：4096 位模幂，Python 原生 `pow` 可承受（分钟级），内存 > 8 GB 更稳。

```python
# 需要至少两组 (s, m)，m 为可猜的摘要（同方向 2 的候选集）
from math import gcd
N = gcd(pow(s1, e) - m1_int, pow(s2, e) - m2_int)
# N 应是 4096 位附近；用第三组 (s3,m3) 验证：pow(s3,e,N) == m3_int % N
```

**成功判据**：得到 ~4096 位、且能用第三组独立验证的 `N`。
**价值**：一旦有 `N`（+`e`），即可**本地验签任意构造的容器**，把"能不能改固件"从真机实验变成纸上实验。

### 方向 5 ★★★ 写一个正确的 AES 验证器（CBC / CTR 双模型）

**为什么需要**
`ks_extract.py` 把 `ct ⊕ 0` 命名为"真实 keystream"——只在 **CTR** 下成立；而报告同时称算法为"AES-CBC/CTR"**模式未定**。命名与模型之间是跳跃。

**要做什么**
用 `ipu_data` 的已知明文全零，对**两种模型**分别构造可判定的检验：

| 模型 | 已知明文全零时的结构 | 可检验的关系 |
|---|---|---|
| AES-ECB | `C_i = E_K(0)` 对所有 `i` | **所有 16 字节密文块完全相同** ⇒ 这是区分 ECB 的**唯一**指纹 |
| AES-CBC | `C₁ = E_K(IV)`，`C_i = E_K(C_{i-1})`（明文全零时是**迭代加密链**） | 块**基本全不同**；与 CTR 在本数据上**不可区分** |
| AES-CTR | `C_i = P_i ⊕ KS_i = KS_i` | `C_i` 即 keystream；同一 key+nonce 下不同分区不应重用 |

> ⚠️ **勘误（2026-10-14，由 `06_密码学重跑` 线程指出并实测证实）**：本节早先版本写作「CBC 且明文全零 ⇒ 所有密文块必须相同」，**这是错的**——"块全同"是 **ECB + 常量明文**的指纹；CBC + 全零明文是迭代链 `C_i = E_K(C_{i-1})`，块基本全不同。
> 自造样本实测：真 **CBC** + 全零明文 → `len(set(blocks)) = 256/256`（全不同）；真 **ECB** + 全零明文 → `1`。

```python
# 唯一能判的判决：块全同 ⇒ ECB；块全不同 ⇒ 只能排除 ECB，CBC 与 CTR 不可区分
ct = raw[0x200+0x47fec00 : 0x200+0x47fec00+0x40000]
blocks = [ct[i:i+16] for i in range(0, len(ct), 16)]
n = len(set(blocks))
print("不同块数 =", n, "/", len(blocks))
# n == 1        → ECB + 常量明文
# n == len(...) → 排除 ECB；CBC 与 CTR 在本数据上不可区分（需密钥 / 同 (key,IV) 下明文被改动的第二份密文 / 运行时 DDR 才能定）
```
**`ipu_data` 实测 `n = 16384 / 16384` ⇒ 只能排除 ECB，不能判定 CBC 还是 CTR。**

### 免密钥的"同明文不同 IV"对照组（本次新发现，可直接用）
`eep_ow_a ≡ eep_ow_b` 与 `eep_act_a ≡ eep_act_b` 的**记录 SHA 相同** ⇒ 在"记录 SHA = 明文 SHA"的前提下，这是**两对天然的同明文、不同 IV** 样本，**无需密钥**即可用来检验任何 keystream/padding 假设（实测逐字节相等率 0.3716% / 0.2930%，XOR 熵 ≈ 8 ⇒ 排除 ECB 与固定 XOR 流）。

**必须写进结论的声明**：本方向**不缩小 2^128 密钥空间**，只提高"否定"与"命中"的可信度。项目在 `29:123,208-211` 已做此声明，继续保持。

### 方向 8 ★★★★★ 用官方 LUMIX Tether 在 `0x2382` 抓包做对照

### 方向 9 ★★★★ 把服务模式的 `SCREEN CAPTURE` / `ERR CODE DISP` 当"第三、第四观测面"

### 方向 17 ★★★★★ E4：分离 RAM 与 flash 的**判定实验**

### 方向 20 ★★★ 长名崩溃的严格阈值实验

**现有设计的三个缺陷**（详见审计 §2，A 级/B 级）：
1. **单位混用**：240 字符在 exFAT 是 480 字节 UTF-16；若按"名字字节"累加，窗口应是 115.7–172.8 KB，而非 58–86 KB。报告未声明按字符还是字节。
2. **量被换了三次**：表格里的"202 KB"是 entry-set 字节，"86 KB"是 `count × namelen`——**同一报告内三个量混用**。
3. **B vs C 对照不干净**：同时变了文件数（360/2160）、名字长度、entry-set 大小。**唯一干净的是 B vs D**，它只支持"长名本身"，不支持 58–86 KB。

**正确设计**

| 项 | 设计 |
|---|---|
| **方案一（推荐）** | **固定文件数 360，变名字长度** 12 / 48 / 96 / 144 / 192 / 240 |
| **方案二** | 固定名字长度 240，变文件数（但文件数与累计字节同步变化，分辨力弱） |
| **额外对照** | **"0xC1 Name 项个数"对照**：等量 0xE0 填充，检验触发量是"字节总量"还是"Name 项个数" |
| **每组重复** | ≥2（因判据是"崩/不崩"单一位） |
| **必做防护** | 正常关机再拔卡；接 AC；触发 boot loop 后拔卡 + 格式化恢复 |
| **报告要求** | 明确声明每个量的**单位**（字符 / UTF-16 字节 / entry-set 字节 / Name 项个数） |

### 方向 21 ★★★ CVE-2019-5096 的"版本 + 存在性"两小步

**现状**：项目直接跳到"需堆控 → 高砖机风险 → 延后"，**跳过了最便宜的一步**。
**要先补的两个缺口**：
1. **版本从未确定**——GoAhead 的 CVE-2019-5096 只影响特定版本区间（3.6.5 / 4.1.1 / 5.0.1）。
2. **代码路径未确认**——S5 的 `senddata` 用**自定义 46 字符边界**（`04:16`），可能是 CGI 自解析而非 GoAhead 内建 multipart 处理器。

| 步骤 | 内容 | 风险 |
|---|---|---|
| **步 1：版本指纹（非破坏）** | 错误页/XHTML 结构、`Server:` 头、对未知方法（`OPTIONS/PUT/DELETE`）与畸形路径的返回码矩阵，与各 GoAhead 版本已知行为比对 | 🟢 低 |
| **步 2：路径确认** | 构造**格式合法但内容异常**的 multipart 到 `senddata`，观察是否走到解析器（返回码变化 vs 通用 `err_param`） | 🟡 低–中 |
| **步 3：存在性（崩溃）探测** | 只发畸形 multipart，观察 500/断连/重启；**不做堆布局** | 🟠 中（可能重启）；**建议在可牺牲机上做** |
| **步 4：堆控** | 仅当步 3 阳性才做 | 🔴 高 |

**还必须分析的一点**（项目完全未提）：**multipart 解析发生在 accctrl 门之前还是之后？** 若在前，则属**未认证可达**，严重性完全不同。

## 第四梯队 · 高风险 / 需硬件

### 方向 23 拆机只读取证 → UART bootlog → JTAG

**顺序很重要**（避免不可逆动作先行）：

```text
① 只读取证：SoC / Wi-Fi / 存储标定丝印 + 测试点照片（零风险，先做）
② UART bootlog：判断 Stubby 是否 ENFORCING（只读引出，低风险）
③ JTAG dump DDR：唯一"不需密钥直达运行时明文"的路
```

**重要限定（来自项目自己的分析）**：A7 有完整 CoreSight，但 **M0 监督核无 CoreSight**，且密钥可能在**独立安全芯片**（`hardware_attack_surface_notes.md:146-151`）⇒ **JTAG 能拿到明文，未必能拿到密钥**。把这条写进预期，避免投入后失望。

### 方向 24 恢复模式（USB）只读入口调研

`oracle/README.md:88-100` 指出"**恢复模式下的固件写入通常跳过签名检查**"——这是目前**唯一未被项目否定**的验证绕过路径。
**只做只读枚举**（扩展 `13_/02_工具` 的 `s5_usb_desc`/`s5_usb_ep0` 到恢复模式），**不写固件**。

### 方向 25 恶意 USB 主机面（畸形 CBW/CDB）

`05_源码/usb-scsi/` 是 **S1R2 的内核导出**（`pvc_mass_storage.c`），显示松下把 CDB 执行放到用户态 ⇒ 存在"恶意主机攻击相机"的解析面。
**前置**：先确认 S5 是否复用同一 gadget（当前只有 S1R2 源码，S5 未验证）。

### 方向 26 chip-off / Crypto Engine 故障注入 / 侧信道

唯一能拿"密钥本身"的路。LAB 级、高成本。**建议在方向 23 之后**——先用 JTAG 确认密钥是否真的在片内、是否有明文可拿。

## 附 B：三条应写入方法学的铁律（补充项目已有的两条）

项目已有（`REPO_CONTENTS.md:67-70`）：
> ① 没有对照组的结论不要写进报告；② "相机报写入错误"不能当作"内存写已执行"的判据。

**本次审计证明这两条不够**——S1 的空操作、S2 的偏移 bug 都不是"缺对照组"，而是**实验/工具本身无效却未被检出**。建议补充：

> **③ 任何"写入类"实验，上传前必须断言 `payload != pre_write_readback`；若相等，立即中止并如实记为"无效试验"。**
> 理由：10-14 受控复测（S1）与 5.9K 实验（项目自己已识别）踩了同一个坑；`persist.py:334` 的 `assert` 只校验字段等于目标值，**不校验与当前状态不同**。

> **④ 任何依赖结构化二进制偏移的结论，必须附一个"偏移判决实验"：用已知明文/已知摘要验证同一偏移模型在多个样本上命中；并在 `TOOLS.md` 登记单一真源。**
> 理由：S2 的 off-by-0x200 让 4 条旗舰结论失效，而项目内有 3 处文档写对、7 个脚本写错，**没有任何机制能发现这种分裂**。

> **⑤ 每个"权威结论文件"必须登记它的"判据侧原始数据"在哪。**
> 理由：18/12/10 档位、`sd_memory` 读数、`startsenddata` 响应文本、`P1000004.MOV` 实拍**全部不在库内**，导致这些数字**不可离线复现**。
