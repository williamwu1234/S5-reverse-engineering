- 单帧 **20–26 ms**（640×432）⇒ 取景流有余量

## 2. 「机内实时烧录」的最终裁决：**不可能**

| 层次 | 结论 |
|---|---|
| 功能层 | Real Time LUT 属 **S5II/S5IIX/GH7/S9/G9M2/S1M2/S1R2**；官方三机对比表的「照片风格」行否证初代 S5 |
| 管线层 | 它是**一个照片风格条目**，需**实时 3D LUT 插值级**并与 JPEG/HEIF、视频编码器串联；S5 的 `MY PHOTO STYLE` 只有参数化调整，**无 LUT 槽位** |
| 可达层 | 跨代不可移植；固件加密 + 签名；无 RCE ⇒ 不是"开关没找到"，是**没有那级硬件管线** |

⇒ 所以把 LUT 做在**取景流那一层**，是本机能拿到的真正"实时套 LUT"。

## 3. ★「无线访问机身存储」定因（本轮实机）

### 3.1 已从官方 APK 取出**确切**的 DLNA 请求（此前项目一直缺这一环）

`p168v5/a.java:212-213`、`p168v5/m.java:83-87`：

```
URL      : http://<ip>:60606/Server0/CDS_control
Headers  : Accept-Charset: UTF-8
           Content-Type: text/xml; charset="utf-8"
           SOAPAction: urn:schemas-upnp-org:service:ContentDirectory:1#Browse
           User-Agent: Panasonic MIL DLNA CP UPnP/1.0
           Host: <ip>:60606
Body     : 单行无空白；子元素**不带 s: 前缀**；含松下私有扩展
           <pana:X_FromCP>LumixLink2.0</pana:X_FromCP>
           xmlns:pana="urn:schemas-panasonic-com:pana"
```

**此前项目（含 iOS 移植版）用的是普通 UPnP 写法（带 `s:` 前缀、无 `pana` 扩展）——格式是错的。**
本轮已把正确格式固化进 `s5_content.py`。

### 3.2 实机结果

| 检查 | 结果 |
|---|---|
| `getstate` | **`err_reject`** |
| `getinfo camsetting` | **`err_reject`** |
| `accctrl&type=req_acc`（首次） | **`err_others_requesting`** ← 关键 |
| `get_content_info&value=0/1` | **`err_reject`**（★**端点存在**，非 `err_param`） |
| DLNA 静态资源（设备描述 / SCPD） | HTTP **200** |
| DLNA 控制面 Browse（**逐字节官方请求**） | HTTP **403** |

### 3.3 两个层次的原因

**① 状态层（可修）**：`err_others_requesting` = 相机端**唯一的"待批复"槽被别的请求占住**
（本项目 `18_…:120` 记载「相机端只有一个『待批复』槽」；`20_…:148` 记载该状态的含义是
"已有其它设备在请求"，且**注册要完成还需要机身侧动作**）。
它会让 `getstate`/`getinfo`/`get_content_info` **一律回 `err_reject`**。

**② 通道层（未解）**：即使清理了槽位，DLNA **控制面**仍 403，而静态资源 200
⇒ 相机对 DLNA 控制做了**单独限制**，且**不是请求格式问题**（官方请求逐字节复刻仍 403）。

### 3.4 关于 `err_unsuitable_app`
本轮在清理过程中观察到新状态 **`err_unsuitable_app`**（"客户端不是合适的 App"）。
**这与本项目记录一致**：`accctrl` 的 `ok_under_research*` 表示相机只给了**受限/研究级**授权。
⇒ 需要让相机把本客户端认作**已批准的 App**，途径是在**机身屏幕上按【允许】**。

> ⚠️ **本轮的操作教训（务必记住）**：我用**自造 UUID** 发起了 `req_acc`，
> 之后又用项目既有 ID 重发，导致 `accctrl` 状态在
> `err_others_requesting` → `ok_under_research` → `err_user_refused` 之间反复跳。
> 项目 `25_操作记录与风险手册` 早已警告：**切勿反复重试 `req_acc`**，会被判为异常 App。
> **正确做法（见 `s5monitor.py: ensure_access()`）**：`req_acc` **只发一次**，
> 然后**轮询 `getstate` 等用户在机身上点【允许】**，最多 20 秒后补一次，之后不再打扰相机。

## 4. 蓝牙（BLE）：**已排除**，不是钥匙

引用本项目 `01_研究报告/20_BLE身份与WiFi门独立_20261013.md` 的实测结论：

| # | 结论 | 强度 |
|---|---|---|
| 1 | **局域网（station）方式完全可行且稳定** | ✓ 实测 |
| 2 | BLE 侧**身份注册成功**（写 `8D08A420` 返回成功） | ✓ 实测 |
| 3 | **BLE 注册的身份并不能打开 Wi-Fi 的 accctrl 门** | ✓ 实测 |
| 4 | 家网侧 `req_acc_g` 返回 `err_param`（取不到握手密钥） | ✓ 实测 |
| 5 | ⇒ **两道门互相独立** | ✓ 实测 |

另外 BLE **只暴露凭据面**（SSID/密码特征），**没有文件传输面**；有效吞吐 ~10–100 KB/s 量级
⇒ 传一张 10 MB JPEG 要数分钟，视频更无可能。

**结论：BLE 可以"注册身份"，但那把钥匙开的是另一道门。文件访问必须走 WiFi 或 USB。**

### 6.2 关键实验：DLNA 403 **与推流无关**（假设已排除）

| 步骤 | 结果 |
|---|---|

### 6.3 真正的机制：**访问控制是"单客户端会话"的**

- 你的监看进程持有 `ok`（有身份、有批准、有 keepalive 心跳）；

- 相机端**只有一个"待批复/已批复"槽**（`18_…:120` 已有记载，本轮再次印证）。

**⇒ 结论：要在 WiFi 上访问机身存储，必须"成为那个已授权的客户端"，而不是在旁边另发请求。**

# 7. ★★★ 突破（2026-10-14 晚）：DLNA 的门就是 accctrl 的 `ok`

## 7.1 「智能手机应用程序需要更新」的解法（本项目早已记录）

**根因**（`04_工具与脚本/campaign2/safe_handshake.py` 开头写得很清楚）：

> 相机端 accctrl **只有一个"待批复"槽**。一次没被清理的 `req_acc` 会留下
> **陈旧 pending 请求**，下一次 `req_acc` 撞上它 → 会话态被污染 → 相机报
> **"invalid login occurred / 需要重启"**。

**解法**：用**发起请求时那个同一 UUID** 发一次 `req_acc_can` 清掉它。

```bash
curl -s -A "LUMIX Sync" \
  "http://192.168.1.131/cam.cgi?mode=accctrl&type=req_acc_can&value=<同一UUID>&value2="
```

**本轮实测有效**（不必重启相机）：

| 时点 | `accctrl` | `getstate` |
|---|---|---|
| 清理前 | `ok_under_research_no_msg` | `err_reject` |
| 发一次 `req_acc_can`（同一 UUID）后 | **`ok`** | **`ok`** |

**三条安全规则**（来自 `safe_handshake.py`，务必遵守）：

1. 清理**必须用同一 UUID**；
2. `err_others_requesting` 时**不要清理** —— 那是别人占着会话，误伤他人请求；
3. **绝不用 `req_acc_can` 去打断一个已 `ok` 的会话**；也绝不快速连发 `req_acc`。

> ⛔ **`req_acc` 频率保护**：短时间多次 `req_acc` ⇒ 相机显示「智能手机应用程序需要更新」
> ⇒ invalid login ⇒ **需要断电重启**。这是相机的自我保护，不是漏洞。

## 7.2 ★ 更正一处长期误判：DM≠「相机对 DLNA 控制做了单独限制」

**实机 A/B 对照（决定性）**：

| `accctrl` 状态 | DLNA `POST /Server0/CDS_control` |
|---|---|
| **`ok`**（完整授权） | **HTTP 500 + UPnP SOAP Fault** `<errorCode>701</errorCode> No such object` |
| `ok_under_research_no_msg`（受限） | **HTTP 403** |

**⇒ 403 不是"相机单独限制 DLNA"，而就是 accctrl 未达 `ok`。**

**判据要点：能收到 SOAP Fault 本身就是"已放行"的证据** —— 403 时相机连请求都不处理，
不会有响应体；返回 UPnP Fault 说明**控制面已经在正常工作了**，只是我们查的对象不存在。

因此原报告 §3.3 的「② 通道层（未解）：相机对 DLNA 控制做了单独限制」**应更正为**：
「通道层的门 = accctrl 的 `ok`；在此之前观察到的 403 是同一道门的不同表现」。

## 7.3 尚未解决的最后一环：ObjectID

`701 No such object` 说明 Panasonic LumixLink 内容树的根对象**不是标准 UPnP 的 `"0"`**。
官方 App 的 ObjectID 由调用方传入（`p154t5/a.java:209  l(str, ip, count)`、
`DlnaWrapper.h(objectID, ...)`），反编译里未见字面量常量。

**下一步**：拿到 `ok` 后跑 `sweep`：

```bash
python3 s5_content.py sweep --cam 192.168.1.131
```

`CANDIDATE_OBJECT_IDS` 已内置 16 个候选（`0/1/2/3/4/10/100/Lumix/LumixLink/DCIM/100_PANA/...`）。
判据：**返回条目** 或 **错误码 ≠ 701** 即为命中。

## 7.4 另一条线索：相机的 **DMS（Digital Media Server）** 开关

官方 APK 里有这些日志字符串（`p182x5/a.java`）：

```
"DMS Enabled"  /  "DMS Disabled"
"DMS Enabled When AppStarted"  /  "DMS Disabled When AppStarted"
"DMS Disabled:For Camera"  /  "DMS StateWatch"
```

⇒ 相机的 **DLNA 媒体服务器是可被相机侧开/关的**，App 只做状态监视。
若 `sweep` 扫完仍无命中，则应考虑 **DMS 未启动**（内容树为空 ⇒ 任何 ObjectID 都 701）。
候选排查：相机菜单里的 **Wi-Fi → 发送图像 / DLNA** 相关项是否需要手动进入。
