**对项目文档 E 系列的两处更正（本工作新增）**

1. **「r,s 是合法标量 ⇒ 支持 P-256 判定」不成立。** 随机 256-bit 整数落在 `[1, n-1]` 的概率是 `1 - 2^-32`（因为 `2^256 - n ≈ 2^224`）。所以「5/5 合法」的观测在**任何** 256-bit 随机数据上都会出现，**不构成 P-256 的证据**。`verify_logic_notes.md` 自己已加了「不证明验签内容」的限定，但该限定比它看上去更弱。
2. **高低 s 混合（3 低 2 高）** 说明签名方**没有**做 low-s 规范化。这既符合「不做规范化的 ECDSA 实现」，也符合「纯随机数」，因此同样**不构成判据**。附带提示：若真是 ECDSA，那么它不是 BIP-62/低 s 规范化实现，这对「能否被某些严格验签器接受」是有意义的，但对我们的问题无帮助。

**Ed25519 排他性检验（同为 64 字节签名 `R||S`，小端）**：5 个版本中只有 **1 个**满足 `S < L`（随机期望 1/16），R 可解码 5/5。**不支持 Ed25519**。

## 2. 方法：为什么「跨 5 版收敛」是一个近乎零误报的判据

ECDSA 公钥恢复公式：

```
Q = r⁻¹ (s·R − e·G)        e = 被签消息的摘要标量
```

给定 `(r, s)` 与**猜测的**摘要 `e`，上式总能算出一个点 `Q`。只有当 `e` 真的是签名时所用的摘要时，`Q` 才是真实公钥。

同一台相机、同一把私钥对 5 个版本各签一次 ⇒ 若某个假设组合正确，**5 个版本必须恢复出同一个 `Q`**。两个错误猜测碰巧给出相同 `Q` 的概率约 `2^-256`。因此：

- 收敛 ⇒ 判据成立且可确认覆盖范围；
- 不收敛 ⇒ 该假设被**排除**（这是本工作的用法）。

**自检（证明工具有检出能力，不是「永远报否」）**：`selftest_synthetic.py` 用**同布局合成固件**验证：

| 项 | 内容 | 结果 |
|---|---|---|
| T1 | 3 个合成固件，签名覆盖 `raw[0x2A0:-512]` + SHA-256，BE | **PASS**（收敛且命中已知公钥） |
| T2 | 覆盖 `raw[0x142C:-512]` + SHA-384 截断 32B，**LE 端序**写回 | **PASS** |
| T3 | 阴性对照：3 个固件用**不同私钥**签同一范围 | **PASS**（0 收敛，无误报） |
| T4 | 覆盖 `raw[0x200:-512]` 且签名区先清零 | **PASS** |
| T5 | 合成 2048-bit RSA 密钥 + PKCS#1 v1.5 填充，`rsa_modulus.try_recover` 恢复 N | **PASS**（29.5 s） |
| T5b | 用第 3 个固件对恢复出的 N 独立验证 `pow(s₃,e,N)==m₃ mod N` | **PASS** |

**最近一次完整自检结果：6 项全部通过**（`selftest_synthetic.py`，约 1 分钟）。

即：**该流水线在真值存在时必定检出**。§3 的「无收敛」因此是有意义的否定证据，而不是工具失灵。

### 3.3 消息候选族的构造（这是本轮的主要工作量）

1. **任务指定 8 个范围**：`raw`、`raw[0x200:]`、`raw[0x2A0:]`、`raw[0x2E0:]`、`raw[0x142C:]`、`raw[:-512]`、`raw[0x200:-512]`、`raw[0x2A0:-512]`，以及自然扩展（各头部前缀、`raw[:0x40]`、`raw[:0x200]`、`raw[:0x2A0]`、`raw[0x2E0:0x142C]` …），每个再叠加「签名区清零」变体。
2. **复合拼接**：`[0:0x40]+[0x2A0:0x2E0]`、`[0:0x200]+[0x2A0:0x2E0]`、`[0:0x220]+[0x260:L-512]`（签名区**移除**）、`[0x200:0x220]+[0x260:]`、`[0:0x200]+[0x2EC:0x142C]` 等。
3. **头部字段清零组合**：`0x40`(CRC)、`0x1C`(机型/版本 id)、`0x24`(时间戳)、`0x3C`(长度) 的**全部 16 个子集** × 8 个基范围 × {原始, 签名区清零}。用于覆盖「先做头部规范化再签名」这一类设计。
4. **直接摘要候选**：分区表 48 条条目各自的 32 字节 `SHA-256(明文)`（`0x2EC + 92i + 0x1C`）直接作为 `e`，以及 48 条摘要拼接后的 SHA-256 / 前 32 字节。
5. **穷尽式连续区间**：取容器全部结构边界
   `{0x000, 0x040, 0x200, 0x20C, 0x220, 0x240, 0x260, 0x2A0, 0x2BC, 0x2C4, 0x2E0, 0x2EC, 0x1400, 0x142C, L-512, L}`，
   对**所有** `start < end` 组合构造消息，每个再叠加 {原样, 签名区清零, 签名区移除}。
   这等价于在结构边界粒度上对「签名覆盖哪个连续字节区间」做**穷尽搜索**。

### 3.4 直接摘要相等性检验（另一条独立攻击线）

「`0x220-0x260` 未必是签名，也许就是**明文存放的摘要**」——例如 SHA-512 恰好 64 字节，或两个 SHA-256。该族假设**不需要公钥**即可判定。检验方式：把 `sig[0:32]`、`sig[32:64]`、`sig[0:64]` 及其逆序与全部 135 个消息 × 13 种哈希的计算结果逐字节比较。

**结果：0 命中。** 该族假设被排除。（注意：若是 HMAC 或带密钥的 KDF 输出，离线不可判定。）

### 3.5 已排除假设清单（明确列举）

以下假设**全部**被跨 5 版收敛判据排除（判据误报率 ≈ `2^-256`，且工具有 §2 的检出能力自检）：

- 曲线：P-256 / secp256k1 / brainpoolP256r1 —— **3 条全部排除**
- 编码端序：4 种全部排除
- 哈希：**11 种摘要构造**全部排除 —— `sha256`、`sha256d`、`sha384`(截断 32B / 全长)、`sha512`(截断 32B / 全长)、`sha1`、`sha224`、`sha3-256`、`blake2s`、`blake2b-256`
- 消息：**602 个不同候选**（按名称去重；各家族条目合计 605）全部排除，其中包括：
  - 任务列出的全部 8 个范围 × 全部哈希 × 全部编码 × 全部端序
  - 全部「签名区清零」与「签名区移除」变体
  - 全部「头部可变字段子集清零」规范化变体
  - 全部结构边界连续区间
  - 分区表内嵌 SHA-256 直接作摘要
- 「64 字节是明文摘要（含 SHA-512 全长）」—— 排除

### 3.6 仍未排除、且**原理上离线不可判定**的可能

- **随机化填充 / 加盐**：PSS、带随机 salt 的签名、任何 `e = H(salt ‖ msg)` 的构造。
- **先解密再签**：若签名覆盖的是解密后的明文或其摘要，而明文不可得（项目已确认密钥固化在芯片内），则离线**原理上**不可恢复。
- **非 ECDSA 原语**：Schnorr（BIP-340 也是 64B = `R.x ‖ s`）、HMAC-SHA-512、两个独立 32 字节随机数/密钥材料等。这些**没有**公钥恢复性质，因此在没有公钥的前提下**无法用离线数学证实或证伪**。
- **签名不在 `0x220`**：64 字节块的语义可能与签名无关（项目早期 `FIRMWARE_FORMAT.md` 就曾记为「64B 随机块（疑似 IV/密钥材料）」）。

| 本项目外部信息笔记 `siegfried82_notes.md` | 「S1M2 结论：……（**推断**为标准 ECDSA P-256……）」 | 是**推断**，不是验证 |

> 注：`0x220-0x260` 的位置固定、长度规整（= 32+32）、四周 64B 全零填充、逐版本变化——这些**结构特征**确实与「逐版本签名样数据」高度一致，也是它被推断为签名的原因。但「与签名假设一致」≠「已证实是签名」，更≠「已证实是 ECDSA P-256」。

## 5. 对「版本字段是否在签名覆盖内」的裁决

### 5.1 裁决：**不可判定**

不是「成立」，也不是「不成立」。理由：

1. 覆盖范围取决于签名方案与实现，而这些**无法从明文容器中读出**（验签逻辑在加密的 loader2/loader3/BootROM 内）；
2. 唯一能在离线条件下判定覆盖范围的手段（ECDSA 公钥恢复 + 跨版本收敛）**未能收敛**；
3. 该 64 字节块**是否**是签名，其证据来源已被上游撤回（§4）。

### 5.2 但以下是**与签名方案无关、可数学确证**的结构事实

由 CRC32 与头部复制关系直接得到（5/5 版本实测吻合）：

| 字段 | 区间 | 在 `crc32(data[0x200:])` 覆盖内？ |
|---|---|---|
| 外层 `0x1C` 机型/版本 id | `[0x1C, 0x20)` | **否** |
| 外层 `0x24` BCD 构建时间戳 | `[0x24, 0x28)` | **否** |
| 外层 `0x40` CRC32 自身 | `[0x40, 0x44)` | 否 |
| 内层 `0x2BC` 机型/版本 id **副本** | `[0x2BC, 0x2C0)` | **是** |
| 内层 `0x2C4` 时间戳**副本** | `[0x2C4, 0x2C8)` | **是** |
| 签名区本身 `0x220-0x260` | `[0x220, 0x260)` | 是 |
| RSA 尾块 | `[L-512, L)` | 是 |

实测前提（全部 5/5 成立）：`stored CRC32 == zlib.crc32(data[0x200:])`；内层头 `0x2A0-0x2E0` **逐字节等于**外层头 `0x00-0x40`；`0x3C == L - 0x200`。

**由此得到的可确证推论：**

- 外层 `0x1C` / `0x24` **不受 CRC32（无密钥）保护**。CRC32 是公开可重算的，因此**能检出**对外层头的篡改的，只可能是某个**带密钥的签名**（若存在且覆盖 `[0x0,0x200)`）。
- 内层副本 `0x2BC` / `0x2C4` **在 CRC32 覆盖内**，且落在 `[0x200, L-512)` 这一区间内——而这是 RSA 尾块在结构上唯一合理的覆盖范围。**因此：只要存在任何覆盖 ⊇ `[0x200, L-512]` 的签名（RSA 或 ECDSA），这两个副本（也就是版本字段本身的值）就被该签名覆盖。**
- 综上：**「版本字段的值」几乎必然被某条链保护**（因为内层副本在 CRC + 大概率在 RSA 覆盖内）；**但「外层那 4 个字节」是否被带密钥签名保护，离线不可判定**。

### 5.3 对项目文档具体假设的裁决

`verify_logic_notes.md` 写：「ECDSA 覆盖范围无公钥无法实测，但按结构**最可能**是外层头（0x0-0x200），即外层 0x24 被 ECDSA 覆盖（判定为强假设，未验签）」。

**本工作的裁决：该具体假设在本轮穷举范围内未被支持。** 我们**直接测试了**「消息 = `raw[:0x200]`」以及 `raw[:0x2A0]`、`raw[:0x2E0]`、`raw[:0x142C]`、`raw[:0x40]`、`[0:0x40]+[0x2A0:0x2E0]`、`[0:0x200]+[0x2A0:0x2E0]` 等包含外层头的全部结构边界区间，并叠加了头部字段子集清零、签名区清零/移除等变体，跨 3 条曲线 × 9 种哈希 × 4 种编码——**没有任何一个组合让 5 个版本收敛到同一公钥**。

也就是说：文档结论**「改版本字段必然破坏 ECDSA」**中的「ECDSA」那一半，目前**没有任何正面证据**；它既没有被验证，也没有通过本文的穷举测试。

### 5.4 对降级攻击判断的实际影响

文档原判断：「改版本需同时改 `0x24` 与 `0x2C4`；改内层 `0x2C4` 会破坏 CRC（可重算）但必然破坏 ECDSA 与 RSA-4096，故降级在文件层面被签名阻断。」

按本轮结论，更准确的表述是：

- **改内层 `0x2C4`**：破坏 CRC32（**可重算**，无秘密）；**若** RSA 尾块确实是覆盖 `[0x200, L-512]` 的签名，则同时破坏 RSA-4096（**无密钥不可重签**）——这一半在结构上是可信的。
- **只改外层 `0x24`（不改内层副本）**：**不触及 CRC32 覆盖区**。能否被检出，完全取决于是否存在覆盖 `[0x0,0x200)` 的带密钥签名——**而这一点本文判定为不可判定**。
- 因此「只改外层 4 字节」是否为一条真实可用的攻击面，**不能由离线数学裁定**；它取决于设备启动时读的是外层还是内层头、以及是否验签外层头。

## 6. RSA-4096 尾块（`L-512 .. L`）

### 6.1 实测与恢复结果

- 5 个版本的尾块**互不相同**、熵 ≈ 7.5–7.6 bit/byte、`S5___V29.sig` 与 `S5___V29.bin` 尾部 512 字节 **逐字节相等**（确证）。
- 恢复方法：`N | gcd(s₁^e − m₁, s₂^e − m₂)`，用第 3–5 个版本以 `pow(s_k, e, N) == m_k mod N` **独立验证**，只在全部通过时才声称成功。
- 填充候选：`raw`（摘要即整数，大端/小端）、`PKCS#1 v1.5`（标准 DigestInfo，按哈希选 DER 前缀）、`PKCS#1 v1.5`（简化 `00 01 FF..FF 00 ‖ digest`）。
- 指数端序：签名字节按大端 / 小端两种解释都试。

| 指数 e | 候选数（msg×hash×padding） | 端序 | 耗时 | 结果 | JSON |
|---|---|---|---|---|---|
| 3 | 3,620 | BE + LE | 0.7 s | 未恢复 | `rsa_result_small_e.json` |
| 5 | 3,620 | BE + LE | 1.6 s | 未恢复 | 同上 |
| 7 | 3,620 | BE + LE | 2.9 s | 未恢复 | 同上 |
| 17 | 3,620 | BE + LE | 9.7 s | 未恢复 | 同上 |
| 257 | 3,620 | BE + LE | 457.8 s | 未恢复 | 同上 |
| 65537 | 24 个高先验候选 × 2 端序 | BE + LE | 3,012 s | 未恢复 | `rsa_result_e65537_p15di.json` |

`e = 65537` 所试的 24 个候选是**按先验排序的前 24 名**（`PKCS#1 v1.5 + DigestInfo` 填充）：

| 序号 | 消息范围 | 哈希 |
|---|---|---|
| 0–4 | `raw[0x200:-512]` | sha256, sha384(截32), sha512(截32), sha1, sha384(全长) |
| 5–9 | `raw[:-512]` | 同上 5 种 |
| 10–14 | `raw[0x2A0:-512]` | 同上 5 种 |
| 15–19 | `raw[0x2E0:-512]` | 同上 5 种 |
| 20–23 | `raw[0x142C:-512]` | sha256, sha384(截32), sha512(截32), sha1 |

（高先验全集共 84 个，可用 `--max-cands-65537 84` 跑完，约需 2.5 小时。）

**未恢复出任何 4096-bit 模数 N。** 因此也**没有任何依据**声称尾块是 RSA-4096 签名——「512 字节 = 4096 bit」只是尺寸上的巧合性一致。

> 说明：`e = 65537` 时 `s^e` 有 2.68 亿位，单次 gcd 约 90 秒（GMP）。脚本默认只跑**高先验子集**并受 `--max-cands-65537` / `--budget` 限制；`--max-cands-65537 0` 之外的完整穷举在时间上不可行，这一覆盖缺口已在 §7 局限中声明。

### 6.2 对项目文档 E9 的更正（推理错误）

`verify_logic_notes.md` E9：

> 「RSA 尾块不是 PKCS#1 v1.5：首字节 `89 a1`（v1.5 应为 `00 01`），512 字节中 511 个非零」

**该推理在密码学上不成立。** PKCS#1 v1.5 里「以 `00 01` 开头」描述的是**编码后的消息 m**，而我们观察到的是**签名值 `s = m^d mod N`**。`s` 在 `[0, N)` 上近似均匀分布，其首字节是 `0x89` 的概率约 1/256 量级——这与填充方式**完全无关**。换言之：

- 「首字节 `89 a1`」**不能**排除 PKCS#1 v1.5；
- 「511/512 非零」同样**不能**排除 PKCS#1 v1.5（`s` 本来就几乎不可能是 0）。

因此本项目此前「RSA 尾块更可能是 RSA-PSS 或裸 RSA」的倾向**缺乏依据**，属于应当撤回的推论。本轮已把 PKCS#1 v1.5 作为**首选**候选重新纳入并以 e ∈ {3,5,7,17,257} + 24 个 e=65537 高先验组合实际测试。

## 7. 局限声明

1. **无公钥 ⇒ 无正面确认。** 公钥恢复是「猜测 + 交叉验证」，只能**排除**假设，不能在没有正确摘要猜测时**发现**真值。本工作给出的是**否定性证据**，不是证明签名不存在。
2. **消息空间是枚举的。** 602 个候选覆盖了「连续字节区间 + 头部规范化 + 复合拼接 + 内嵌摘要」这几大族，但**不覆盖**：加盐/域分隔前缀、随机化填充（PSS）、覆盖解密后明文、覆盖容器之外的数据、非连续/交错的消息布局。
3. **`e = 65537` 的 RSA 覆盖不完整**：单次 gcd 约 60–90 s（2.68 亿位运算数），因此只跑了**先验排序前 24 名**（PKCS#1 v1.5 + DigestInfo）在 BE/LE 两个端序下，共 48 次 gcd（3,012 s）。高先验全集 84 个、全部 `(msg,hash,padding)` 3,620 个**未跑完**。可用 `--max-cands-65537` / `--budget` / `--pads` 扩跑。
4. **「不是 ECDSA」无法证明。** Schnorr、HMAC-SHA-512、两个独立随机 32 字节值等在无公钥/无密钥时**原理上**不可区分。
5. **依赖外部库的正确性。** 主结果由 `python-ecdsa 0.19.2` 产出；P-256 路径同时用本文件内置的**独立纯 Python 实现**交叉验证（30 组随机签名上两套实现的恢复集合完全一致，`selftest_synthetic.py` T1–T4 通过）。非 P-256 曲线（secp256k1、brainpoolP256r1）只经库实现，未做第二实现交叉验证。
6. **`gmpy2` 依赖**：RSA 部分用 `gmpy2 2.3.2`（GMP）加速；无它时脚本回退到 Python 内置整数，结果等价但 `e=65537` 会极慢。
7. **未做的事**：不解密固件、不连接相机、不访问 `192.168.1.131`、不上传任何数据、不修改任何既有文件。

```bash
python3 ecdsa_recover.py --root <项目根> --profile all --deep --exhaustive \
        --json out_full.json

# 3) 只想跑穷尽边界集合
python3 ecdsa_recover.py --root <项目根> --profile none --exhaustive --mode recover

        --max-cands-65537 24 --pads p15_di --budget 0 --json rsa_65537.json
```
