## 一、取景流协议

```
GET http://<相机IP>/cam.cgi?mode=camcmd&value=recmode        切拍摄模式
GET http://<相机IP>/cam.cgi?mode=startstream&value=<UDP端口>  相机把流发到该 UDP 端口
      ↓
UDP 上收到 MJPEG：每个包内含完整 JPEG（SOI ff d8 … EOI ff d9）
      ↓
GET http://<相机IP>/cam.cgi?mode=stopstream                   停止
```

| 项 | 实测值 |
|---|---|
| 编码 | **MJPEG**（每包一帧） |
| **分辨率** | **640 × 432**（3:2，与传感器一致） |
| 原始帧率 | 相机平均 **~30fps，但为突发式** |
| 单帧大小 | 约 25 KB |
| UDP 端口 | 49152（官方允许 49152–65535） |

**⚠️ 相机强制单流会话**：上次没 `stopstream` 干净关闭，新的 `startstream` 会返回
`<result>err_busy</result>`。本工具的做法是**先 stopstream 清场 + 退避重试 4 次**。

## 二、为什么最终选「固定 18fps」

相机的流是**突发式**的（逐 250ms 采样：`0,8,6,0,0,2,16,8,0,…`，250ms 内最多 16 帧 ≈ 64fps）。

| 播放策略 | 结果 |
|---|---|
| 追相机速率（30fps） | 队列被抽干 ⇒ 空档时垫帧 ⇒ **画面定住**；或积压 ⇒ **延迟堆到 1266ms** |
| **固定 18fps + 只取最新帧** | ✅ **延迟 0ms、抖动 2ms、零停顿零跳帧** |

**⇒ 这就是官方 App 的做法**（640p @ 18fps）。
诊断里的「**主动抽帧**」计数就是这件事 —— 相机送 30fps、我们放 18fps，必然丢帧，
但**永远显示最新的那一帧**，所以画面是**均匀的 18fps**，不是忽快忽慢的跳帧。

**可调参数**（`s5monitor.py` 顶部）：
```python
PACING_MODE = "fixed"     # fixed=官方风格；adaptive=队列反馈控制
PACING_FPS  = 18.0        # 输出帧率
FIXED_KEEP  = 3           # 最多保留 3 帧（≈170ms），抗短空档
KEEPALIVE_SEC = 10.0      # 心跳间隔
```

### 心跳的两难（实测）

| 心跳间隔 | 结果 |
|---|---|
| **不发心跳** | 相机约 **13 秒后停流** ❌ |
| 每 2–3 秒一次 | 相机**持续繁忙** ⇒ 流反复卡顿 ❌ |
| **每 10 秒一次**（且状态走服务端缓存） | **稳定，零停顿** ✅ |

**根因**：`getstate` 在相机侧耗时 1–3 秒，期间**取景流被挤停**。
**对策**：① 服务端缓存状态，浏览器轮询不打相机 ② 心跳固定 10 秒。

## 三、控制命令（逐条对照官方 APK 还原）

| 功能 | 命令 | 备注 |
|---|---|---|
| **触摸对焦** | `camctrl?type=touch&value=<x>/<y>&value2=on` | ★ **斜杠分隔**，且**必须带 `value2=on`** |
| 释放 | `camctrl?type=touch&value=0/0&value2=off` | 抬起时发 |
| 移动 AF 点 | `camctrl?type=touchaf_chg_pos&value=<x>/<y>` | |
| AF 区域 | `camctrl?type=touchaf_chg_area&value=up\|down` | |
| AE 锁定 | `camctrl?type=af_ae_lock&value=on\|off` | |
| **焦点驱动** | `camcmd?value=tele-normal` / `wide-normal`（还有 `-fast`） | capability 明确列出，**稳定可用** |
| 停止驱动 | `camcmd?value=focus-stop` | |
| 拍照 | `camcmd?value=capture` | |
| 录像起/停 | `camcmd?value=video_recstart` / `video_recstop` | |
| 模式 | `camcmd?value=recmode` / `playmode` | |
| 读对焦模式 | `getsetting?type=focusmode` | 返回 `<settingvalue focusmode="afs">` |

### ⚠️ 最容易搞错的一条

**`camctrl type=focus` 是【变焦】不是对焦！**
（值：`tele-normal` / `tele-fast` / `wide-normal` / `wide-fast` / `focus-stop`；
官方 UI 里它属于 `LiveViewLumixZoomView`）

### 相机不支持的命令（实测）

| 命令 | 结果 |
|---|---|
| `camctrl?type=asst_disp`（峰值显示） | `err_param`（参数格式未找到） |
| `camctrl?type=change_disp_mag`（放大辅助） | `err_reject`（值已按官方规范用 300–2000，仍被拒） |

## 四、错误码语义（实测）

| 返回 | 含义 | 处理 |
|---|---|---|
| `ok` | 成功 | — |
| **`err_param`** | **参数格式错** | 检查格式 |
| **`err_reject`** | 格式对，但**相机当前状态不接受** | **重试**（状态会翻动） |
| **`err_busy`** | 相机忙 | **退避重试** |
| `err_critical` | 严重状态错误 | 重启相机 |
| `err_user_refused` | 相机内部校验拒绝 | 重新走流程 |

### ★ 关键机制：授权状态在「翻动」

实测日志（逐条可见）：
```
状态 = ok  →  ok_under_research_no_msg  →  ok  →  ...
```
`camctrl` **只在"恰好是 `ok`"的那一瞬间成功**。

**⇒ 本工具的对策**：`camctrl` / `camcmd` 对 **`err_busy` 和 `err_reject` 都做退避重试**（最多 8 次），
**一直撞到 `ok` 窗口为止**。这一改把触摸对焦从"偶尔成功"变成 **实测 8/8 = 100%**。

## 五、`accctrl` 会话（授权）

```
GET cam.cgi?mode=accctrl&type=req_acc&value=<设备ID>&value2=<设备名>
      ↓
返回： <状态>,<相机名>,<模式>,<加密标志>
      例： ok,S5-XXXXXX,remote,encrypted
```

| 状态取值 | 含义 |
|---|---|
| **`ok`** | **完整授权**（camctrl 可用） |
| `ok_under_research_no_msg` | 受限；相机未显示待批消息 |
| `ok_under_research` | 受限 |
| `err_user_refused` | 相机内部校验拒绝 |

- 设备 ID 格式：**`4D454930-0100-1000-8001-` + seed**（逆向自官方 APK）
- 相机名 `S5-XXXXXX` 与 **BLE 广播名一致**（交叉验证）

### 🔴 血泪教训：`req_acc` 绝不能高频重发

排查中把 `ensure_access` 改成「每 10 秒重发一次 req_acc」后：

```
相机屏幕显示：
    「智能手机应用程序需要更新」
        ↓
    invalid login
        ↓
    要求重启相机
```

**⇒ 相机把"短时间内大量连接请求"判定为异常/过旧的 App，直接封禁。**
**⇒ 只能靠断电重启恢复。**
**⇒ 正确做法：`req_acc` 只在启动时发【一次】，之后只轮询 `getstate`。**

**另更正一个误区**：相机**不会弹出任何授权对话框** —— 全程是相机内部自己校验。

## 六、SSDP "alive" 上报

官方 App 的 `DlnaWrapper.advertisementStart()`（native `dlnaCore`）会向网络广播自己的存在。
本工具已复刻：向 `239.255.255.250:1900` 发 **SSDP alive NOTIFY** + **M-SEARCH**（每 20 秒重发），
并提供 `/desc.xml` 供 SSDP `LOCATION` 引用。

## 七、安全边界

**只发送**：`camcmd`（拍照/录像/变焦/模式）、`camctrl`（触摸对焦/AE锁定）、
`getstate`、`getsetting`、`getinfo`、`startstream`/`stopstream`

**代码内置白名单，永不发送**：固件升级、格式化、重置、关机、配置上传、任何有副作用的命令

## 八、排错速查

| 现象 | 原因 | 处理 |
|---|---|---|
| `startstream → err_busy` | 相机侧有残留流会话 | **相机断电重启** |
| 相机提示 `invalid login` | `req_acc` 被高频重发 | **相机断电重启** |
| 触摸对焦时好时坏 | 授权状态翻动 | 已内置重试；隔 1 秒再点 |
| 页面全黑、fps=0 | 没在拍摄模式 / 流没起 | 点「◉拍摄」；或停流再开 |
| 画面卡 | 看 📊 诊断归因 | 若「下发慢」=0 且「相机侧空档」大 ⇒ 相机侧突发，已被缓冲吸收 |
| 端口被占用 | 上次实例还在 | `pkill -9 -f s5monitor.py` 或换端口 |
