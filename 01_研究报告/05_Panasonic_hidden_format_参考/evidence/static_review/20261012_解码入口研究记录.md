# 解码入口研究记录

日期：2026-10-12。目标：尽可能恢复 S1H V2.8 更新包中的程序/资源结构；所有结论均限于当前固件样本与只读核验。

## 已核实的容器偏移

对普通分区，分区表的 offset 字段加 `0x200` 后与文件末端和可读分区摘要核验相符：S1H 最后一项终点为 `0x56cbe00`；S5 V2.9 为 `0x560ee00`。S5 的 7 个 type 2 条目在正确基准下 SHA-256 全部匹配。早前“所有分区都统一加 0x200”的概括过宽：S1H 的 loader1/2/3 属特殊连续区，不能套用普通分区基准。

S1H 主分区表从绝对 `0x2dc` 起，53 项、每项 92 字节，终点是 `0x15e8`。loader1/2/3 的 offset 字段分别为 `0`、`0x1000`、`0xa800`；以 `0x1600` 为该组数据起点，可得到连续范围：loader1 `[0x1600,0x2600)`、loader2 `[0x2600,0xbe00)`、loader3 `[0xbe00,0x17e00)`。对应载荷熵均约 7.956/7.996/7.996。该组起点在目录结束后的 `0x18` 字节边界间隔处；普通分区则按 `offset+0x200` 核验。

## 对“loader2 明文目录”的纠正

公开分析报告称 loader2 开头有 11 项明文目录。按错误的 `offset+0x200` 读取 loader2，会从 `0x1200` 开始，恰好读到主分区表尾部；该 11 项的名称、大小和摘要因此能与主表吻合，并非第二份目录。正确 loader2 起点是 `0x2600`，熵约 7.9956，`nr_data`/`hr_c_ddr` 字符串均不存在。当前没有解密载荷。

## 之前结论的更正

此前记录把表尾写成 `0x15f8`，并据此判断目录与首段之间的边界；该计算有误。正确表尾为 `0x15e8`。此前把 loader1/2/3 按普通分区统一套用 `+0x200` 也有误。新记录已按特殊连续区重新定位，并撤回“loader2 有独立明文目录”的判断。

## 证据与限制

- `20261012_loader_offset_false_directory_check.json`：原始偏移、校验和、熵、边界关系与误判复现。
- `S1H_V28_function_audit.json`：普通分区的结构与熵审查；其中 loader1/2/3 旧 `offset` 字段为错误解释，不应引用这些位置结论。
- 第三方解包器目前被静态检查到直接按表内 offset 切片；因此对 S1H loader1/2/3 会产生上述误定位。此结论不代表该工具在所有 Panasonic 格式均错误。

本轮是布局误判的纠正和真实 loader 定位，不是解密突破；密钥、可执行代码、传感器时序、可修改入口与可刷包仍未得到。
