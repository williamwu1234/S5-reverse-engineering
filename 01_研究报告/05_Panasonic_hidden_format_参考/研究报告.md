## 1. 摘要

在受测 S1H 上，完整菜单 `allmenu` 声明的录制质量词汇和当前菜单 `curmenu` 的启用项存在差异。在普通 MP4 上下文，部分 `mp4ed_*` 条目被当前菜单标为可用，却没有在已采集的完整菜单中声明对应设置写命令。使用既有 `setsetting` 接口选中其中一个条目，可以使录制格式读回为 `mp4ed`，机身原厂菜单显示为 **MP4（LPCM）**。

已验证档位 `mp4ed_25p_400mbps_4k_10bit`：实际视频为 3840×2160、25fps、H.264 4:2:2 10bit、全部 I 帧，音频 LPCM。录制质量菜单显示 FULL、ALL-I、400Mbps，并出现原厂质量列表。用户确认一次正常关机开机，随后视频仍显示该档位。

这个结果说明固件已有配置和显示逻辑可以被网络设置入口选中。它没有证明固件被修改，也没有证明新增性能：原厂 MOV 已有对应画面编码档位。S5 能否沿用相同 token、显示相同菜单、录出相同媒体，必须分别验证。

## 2. 范围、环境与证据等级

受测机：DC-S1H，原厂固件 V2.8；PAL／50Hz 环境。实机能力响应机型为 S1H，状态响应版本字段为 VD3.60；后者是接口状态字段，不应当写作固件版本。历史实验期间用户曾开启工程模式，但未进行开启／关闭对照，不能据此断言工程模式是必要条件或普通零售状态必然可用。

使用本研究编写并审阅的限定网络程序。没有执行第三方归档中的上传、崩溃、RCE、密钥猜测或刷写程序。S5 开发者截图和报告提供了接口线索，其实机结论属于第三方材料。

| 等级 | 验证方式 | 可以支持的结论 |
|---|---|---|
| E1 | 原始菜单响应 | 固件在该上下文列出／启用某个候选 |
| E2 | setter 返回 ok，连续精确读回，配置变化 | 设置被接受；不等于能录制 |
| E3 | 机身菜单照片／视频 | 原厂 UI 确实显示该档位；不等于媒体属性 |
| E4 | 实际媒体及完整软件解码 | 文件编码、尺寸、帧率、音频等成立 |
| E5 | 用户确认正常重启及事后菜单视频 | 本次正常重启后保留；不覆盖恢复出厂等条件 |

## 3. 实现机制

### 3.1 接口路径

设备 Wi-Fi 可达后，通过以下只读请求识别机型、状态、可见值和菜单：

```text
GET /cam.cgi?mode=getinfo&type=capability
GET /cam.cgi?mode=getstate
GET /cam.cgi?mode=getinfo&type=allmenu
GET /cam.cgi?mode=getinfo&type=curmenu
GET /cam.cgi?mode=getsetting&type=videoformat
GET /cam.cgi?mode=getsetting&type=videoquality
GET /cam.cgi?mode=getinfo&type=camsetting
```

`allmenu` 的 `cmd_mode=setsetting, cmd_type=videoquality, cmd_value=…` 给出声明值；`curmenu` 的 `id=menu_item_id_v_quality_<token>, enable=yes` 给出当前可用性。对两者作集合差，得到有本机证据的候选，而非任意字符串枚举。

### 3.2 S1H 已验证的选择流程

1. 确认机型，且 `rec=off, cammode=rec`；记录原格式、原质量和二进制配置快照。
2. 用正常设置入口转为普通 MP4；保存该格式原先记忆的质量。
3. 再读取当前菜单，确认目标 `mp4ed_25p_400mbps_4k_10bit` 为 `enable=yes`。
4. 单项写入：

```text
GET /cam.cgi?mode=setsetting&type=videoquality&value=mp4ed_25p_400mbps_4k_10bit
```

5. 两次读取质量均为目标；读取格式为 `mp4ed`；检查录像仍停止。
6. 用户到原厂菜单查看标签与质量列表，用物理录像键生成测试文件。

此处没有修改字符串资源或菜单代码。**显示变化由原厂固件自行完成**。受测机无需依靠执行自制代码完成这一步；此实验没有证明任何形式的任意代码执行。

交付程序为减少影响，要求使用者先在机身选择普通 MP4，避免通用脚本自动跨多个格式。它只写一个已启用候选，不复刻历史实验的批量测试。

### 3.3 状态与恢复

S1H 的 CAMSET 响应为 66,933 字节，已解析 848 个记录；记录起点 0x34，记录结构为 u16 tag／u16 总长度／u16 flag／payload，终止标记 ffff／0000。受测快照字节和模 256 为 0。对具体字段的理解来自多次已知值切换与差分，不代表 S5 采用相同结构。

本机已确认的记忆项：tag 0x124 为 MOV 质量、0x123 为普通 MP4 质量、0x16e 为 MP4ed 质量、0x122 为 AVCHD 质量、0x5e 首字节为格式编号。观察到格式编号 MOV=6、普通 MP4=5、MP4ed=7、AVCHD=0。这些编号属于本机样本，不应直接写入 S5。

恢复仅当前格式和质量会漏掉其他格式的后台记忆项。本机历史基线的 MP4ed 质量为 `mp4ed_50p_100mbps`；完整恢复曾按该原值恢复 MP4ed，再明确切回普通 MP4 恢复其原质量，最后回到原 MOV 质量。涉及异常 AVCHD 切换时还恢复了 AVCHD 记忆项。最终快照逐字节相同，才支持完整恢复结论。不能把本机历史基线用作他人相机默认值。

通用程序保存快照但不回灌。跨机型仅自动恢复 getter 实际读到的原可见值，并报告快照是否一致；未知后台值不猜测、不写入。

## 4. 实机结果

### 4.1 实际媒体

| 档位／文件 | 文件验证 | 状态 |
|---|---|---|
| `mp4_25p_10mbps`／P1022640.MP4 | 1280×720，25fps，H.264 8bit 4:2:0；180 帧／7.2秒；AAC | 实际媒体已解码 |
| `mp4ed_25p_400mbps_4k_10bit`／P1022641.MP4 | 3840×2160，25fps，H.264 High 422 Intra，yuv422p10le；168 帧／6.72秒；所有帧 I／关键帧；PCM s16be、48kHz、双声道 | 视频音频完整解码通过 |

第二个文件为 223,826,574 字节，容器 major_brand 为 `mp42`。黑场样片的视频轨道平均码率约 252.128Mbps，含封装开销的文件平均码率约 266.460Mbps。400Mbps 是菜单标称档位，不能将其写成实测恒定码率。

对应 SHA-256：

```text
P1022640.MP4  b83395a3902c5a1b4cd73a30913f69436e36bbea53742297d3870b961802bd7d
P1022641.MP4  a579a0ff325ed380ac8f6162421f8a382a19c9597e997fd6cf53aed072f19059
```

原厂手册 p260 已列 MOV 对应的 4K25／422／10bit／ALL-I／400Mbps。新增发现是 MP4＋LPCM 的组合及其 UI 可达性，没有证据证明更高传感器性能。

### 4.2 原厂菜单与重启

`evidence/native_menu.png` 显示：MP4(LPCM)、Full-frame、3840×2160／25.00p、传感器输出 25.00p、422／10bit／ALL-I、400Mbps、LPCM，质量列表第 1/3 页，当前条目高亮，Q“添加到列表”可见。

用户确认一次正常关机开机；事后菜单视频保持上述格式和质量。重启全过程没有被拍下，因此是用户陈述与事后视觉证据共同支持。不能扩大到拔电池、恢复出厂、升级固件后的保留。

**限制：打开“录制文件格式”选择器时出现空白框。** 质量列表可显示，但没有证据证明 MP4(LPCM) 已成为正常格式选择器里永久新增的可选项。

原厂手册 p265 说明 Q“添加到列表”会同时登记系统频率、录制文件格式、视频图像区域。保存此隐藏档位后能否从 MOV 经“我的列表”重新进入，是有依据的下一项实验；当前没有完成，不纳入已实现功能。

### 4.3 其他候选与失败案例

在所测普通 MP4 上下文共核对 16 个未在 allmenu 声明的启用候选，其中 14 个准确读回，仅 2 个取得实际媒体。完整 token 与结果见 `evidence/candidate_results.md`。

- `mp4ed_50p_150mbps_4k` 返回 ok，但在写后 1.51／2.99／4.17秒连续读回 `avchd_50p_28mbps`，且格式成为 AVCHD；不能统计为 4K50 成功。
- `mp4hevc_25p_72mbps_4k_10bit` 写入返回 ok，getter 返回 err_critical，停止重复实验。
- 曾出现远程开录后停止命令返回 ok、实际仍在录制的情况。后续改用机身按钮；交付程序禁止发送录像控制命令。
- 先前一次目录未出现新文件，只能说明未取得对应文件；后来的 P1022641 实际样片填补了该档位验证缺口。

## 5. 固件静态研究成果与未解问题

S1H V2.8 原映像：91,012,608 字节，SHA-256：

```text
a3cc5c88cde50f5980acb67f849a33d74432effc9a8e4d3ab95b56b7e13f0514
```

已解析容器目录 53 条记录；表始于 0x2dc，普通目录载荷偏移以 0x200 为基准。loader 使用另行核对的 0x1600 基准：loader1 [0x1600,0x2600)，loader2 [0x2600,0xbe00)，loader3 [0xbe00,0x17e00)。此前公共解析器所谓 loader2 明文目录来自错误偏移读到了目录尾部，不是程序解码突破。

程序与资源载荷尚未获得可验证明文；没有密钥、可执行运行时转储、传感器读出时序、自制代码加载路径或安全可刷包。隐藏格式结果走的是配置接口，与固件载荷解密无因果等价关系。

S5 第三方 V2.9 映像的独立核验修正了旧报告偏移错误：普通偏移以 0x200 为基准，7 个 type 2 原始载荷摘要匹配，type 3 未匹配。loader1 不应按旧错误偏移解释为几乎全零。此处是容器解析修正，不是 AES 破解。对应核验文件在 `evidence/static_review/`，未分发原厂固件。

## 6. S5 迁移方案

### 6.1 可迁移部分

可以迁移 HTTP 请求结构、菜单集合差方法、单项写后连续读回、原厂菜单目视确认和实际文件完整解码的方法。程序支持机型精确识别 S1H 与原始 S5，不把 S5II／S5IIX／S5M2 等视作同型号。

### 6.2 尚不能保证的部分

第三方 S5 截图报告 `mov_50p_50mbps` 写入后变为 `mov_50p_100mbps_10bit`，恢复原值后状态 ok。这是第三方陈述，未由本研究在 S5 上复现。不同读回可能是规范化、别名映射、上下文回退或无效索引，不能直接解释成隐藏性能档位。

相同传感器、相近命名、共享 CGI 接口不构成跨机型可用性证明。S5 可能没有相应 MP4ed 候选；即使候选启用或精确读回，也可能不显示菜单或不录制。

### 6.3 验收条件

1. capability 确认原始 S5；记录机身固件版本、系统频率、镜头及工程状态。
2. 本机 curmenu 对候选明确 enable=yes；保存 allmenu、curmenu、原值和原快照。
3. 单项 setter 成功，连续读回准确，格式与目标家族一致，录像仍停止。
4. 机身录制格式和质量界面显示，照片／视频记录。
5. 物理按键录制文件完整解码，核对实际尺寸、帧率、像素格式、帧类型、音频和容器。
6. 正常重启保留及切回普通格式后重新进入分别测试；两者不可混为一个结论。
7. 恢复可见原值；对完整恢复另看快照逐字节一致性。

未完成 4、5 之前，只能称作接口选择实验成功。没有 enabled 候选时，程序结束于只读发现，不扩大到猜值或注入。

## 7. 复现程序与分发说明

`programs/lumix_hidden_format.py` 是为分发重新整理的标准库实现。它限定 RFC1918 IPv4、禁用代理和 HTTP 重定向、限制响应 4MiB、固定操作白名单、保存请求原文和散列、默认只读、禁止录像／升级／上传命令。activate 只处理当前本机已启用的单一 MP4／MP4ed token，遇到异常尝试恢复可见原值；失联时不能保证恢复。

S1H 的新程序只允许两个已获得媒体的目标；两个已知异常 token 在所有机型上暂时阻止测试。这是基于历史失败证据的保守限制，不宣称异常在 S5 必然复现。

关键历史请求归档在 `evidence/s1h_activation/`；它们证明旧实验的实现过程。新程序通过离线模拟，包括错误机型、禁用候选、未确认写入、S5 实验开关、异常读回和写响应丢失后的回退；没有在本次封装中重新写入研究机，也未在 S5 上运行。
