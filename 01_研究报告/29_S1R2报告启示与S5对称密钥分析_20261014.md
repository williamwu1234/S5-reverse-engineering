## 3. ★★★ 新发现：**零明文区段 ⇒ 纯 `E_K` 链**（S1R2 报告里没有）

### 3.1 实测数据

```
history 明文（type=2，固件里直接可读）:
   共 16,384 块，其中【16,353 块全为零】
   只有第 1 块 + 另外 31 个块非零
```

### 3.2 这在 CBC 下的含义

```
C1 = E_K(P1 XOR IV)          ← 第 1 块，P1 含一个 64 字节头
C2 = E_K(P2 XOR C1) = E_K(C1)     ← P2 = 0
C3 = E_K(P3 XOR C2) = E_K(C2)     ← P3 = 0
C4 = E_K(C3)
   …
```

**⇒ 从第 2 块起来就是一条纯 `E_K` 迭代链，与 IV 完全无关**：
```
C(n+1) = E_K(C(n))
```
**⇒ 一份【16,383 组】已知的 AES 输入/输出对** ✅

### 3.3 由此得到的**极快密钥验证器**

| 验证方式 | 每候选代价 |
|---|---|
| 明文 SHA-256 预言机（原方案） | 解密 131 KB + SHA-256 ⇒ **约 10^5 周期** |
| **零块链判据（新）** | **1 次 AES 块加密 ≈ 40 周期** |

**⇒ 快约 3 个数量级** ✅

粗算吞吐（AES-NI，8 核 @3GHz）：
```
≈ 6 × 10^8 候选/秒
  2^32 → 约 7 秒
  2^40 → 约 30 分钟
  2^48 → 约 5.4 天
  2^128 → 仍不可行
```

**⇒ 它把"验证"加速了，但没有把"搜索空间"变小。** ⚠️

## 4. ★★ 我们的独有资产：**ROM BACKUP 的 `eep_adj` / `eep_fix` 明文**

S1R2 团队**没有**这个。我们有：

| 文件 | 大小 | 熵 | 零字节 | **全零 16 字节块** | 固件同名分区 |
|---|---|---|---|---|---|
| `ADJUST.bin` | **131,072 B** | 1.6250 | 85.5% | **6,844 / 8,192（83.5%）** | `eep_adj` 131,072 B type=3 ✅**大小完全一致** |
| `FIX.bin` | **131,072 B** | 2.2980 | 75.6% | 4,591 / 8,192（56.0%） | `eep_fix` 131,072 B type=3 ✅**大小完全一致** |

`ADJUST.bin` 开头即机身序列号：
```
584a4c32313034323730303135…  = "XJL2104270015"   （与 CAMERA INFO 一致）
000107ffff                   = ADJUST 0x001C 处的已知字段
4d584431443433303032323139…  = "MXD1D43002219"
```

### 意义

1. **这把"已知明文"从"猜"变成了"确知"** —— 而且量巨大（各 131 KB）
2. **`eep_adj` 有 83.5% 的块全零 ⇒ 固件里对应位置也是零块链** ⇒ 可用 §3 的极速判据
3. **两份不同来源的明文（ROM BACKUP + 固件）可交叉验证**候选密钥是否正确

> ⚠️ **注意**：ROM BACKUP 拿到的是**本机的当前值**，固件里是**出厂镜像**。
> 开头（序列号等）必然不同，但**大段零区应一致** ⇒ 仍可作**部分已知明文**。

## 6. ⚠️ 一处**与 S1R2 报告的分歧**：`0x9606` 地址参数

S1R2 报告把 **"PTP `0x9606` 地址参数疑似不校验"** 列为**第 3 优先路线**（不需拆机）。

**但我们项目已经审计过并关闭了这条路线**：

| 我们项目的结论 | 依据 |
|---|---|
| `0x9606` 负载 = `[Size][Addr][DataType]`（32 位 12 B / 64 位 16 B） | 离线审计 Tether 2.12 arm64 ✅ |
| **地址来自相机 `0x9605` 的回复**，客户端协议上可覆盖，相机侧校验未知 | 已确认 |
| **要到达可测试状态，必须先发 `0x9406/0x00090013`（FWUP Request）** | 已定位 |
| `0x9406/0x00090013` **疑似先擦除目标区** ⇒ **高砖机风险，且无安全恢复**（SD.DAT 有砖机史） | 判定 |
| **且数据仍必须通过签名校验** ⇒ **拿不到执行自编代码的能力** | 判定 |

**⇒ 建议**：请 S1R2 团队说明他们**如何在不触发 `0x00090013` 的前提下**进入数据传送态。
如果确有办法，我们再重新评估；否则维持关闭判定。

> **⚠️ 项目红线不变**：**永不发送 `0x9406` 子码**（8 个子码全为带副作用动作）。

## E1. ★ 严重数据错误：首块偏移错位 0x200（同事完全正确）

**我的错误**：
```python
raw[doff : doff+size]            # ❌ doff 是相对【外层数据基址 0x200】的偏移
raw[0x200+doff : 0x200+doff+size]  # ✅ 正确
```
**后果**：我导出的 **35 条记录的「首块密文」全部来自错误切片**。

**我的独立复核（决定性证据）**：

```
history 是 type=2【明文】分区
   目录里的明文 SHA-256 = 8a39d2abd3999ab73c34db2476849cdd…  （= 全零 262144 字节的 SHA-256）
   我的切片 raw[0x1E01400] 首块 = cb078899…   ❌ 非零（但明文应全零！）
   正确切片 raw[0x1E01600] 首块 = 00000000…   ✅ 全零
   全零块数：我的 16352 / 正确 16384
⇒ 铁证成立。
```

**⇒ 原稿那句「history 前 64 字节有一个非零头」是错的** ——
那是**前一个分区（`eep_adj` 尾部）的字节**，**不是 history 本体**。

### E1.1 连带纠正：同事指出的「CBC 矛盾」也是本错误的产物

同事指出 JSON 中 `music`/`koutei_kao`/`zboot` 三条「首块密文相同而 IV 不同」，
在 CBC 下不可能 ⇒ 判定数据不能照用。

**我的复核**：
```
用【错误偏移】检查 ⇒ 存在矛盾（同事观察正确）
用【正确偏移】重查 ⇒ 矛盾条数 = 0  ✅
```
原因：错位切片使相邻分区**共同读取了同一段邻居字节**，导致首块"相同"。

**⇒ 修正偏移后，35 条判据内部自洽（0 矛盾）。**
**⇒ 结论修正为：错误数据不可用；修正数据可用。**

## E3. 判据表述的降级（同事正确，采纳）

| 原稿说法 | 修正后 |
|---|---|
| "精确预言机，无条件" | **带模型前提的筛选条件**：需先确认①标准 CBC ②IV 用法 ③摘要覆盖阶段 |
| "整条链与 IV 无关" | **递推式** `C_i = E_K(C_{i-1})` 不含 IV，但**链的起点由 IV 决定** ⇒ 不能说"与 IV 无关" |
| `history/ipu_data` 投入"双密文解密相等式" | **错**。两者是 (type2, type3)，应使用**单密文判据**：<br>`D_K(C_ipu,1) XOR IV_ipu == P_history,1`，<br>且 `P_history,1 = 0` ⇒ **`D_K(C_ipu,1) == IV_ipu`** |
| 零块链 = "已知 AES 输入输出对" | 降级为 **「候选零内容约束」**；若消费者确认标准 CBC 与摘要覆盖，则为 16,383 条相邻递推约束 |

**⇒ 关键诚实点**：模式、尾字段语义或明文假设**任一项错，都会拒绝真密钥** ⇒ 不能称"无条件精确"。

| 4 | S1R2 的 `0x1000000000000` = 2^44 | **实为 2^48** |
| 5 | "2^48 约 5.43 天" vs "几小时" | **自相矛盾**；二者均为估算，**无实际吞吐日志** ⇒ 已删除"几小时" |
| 6 | "两份独立分析互相印证" | **不成立** —— 后一份沿用前一份假设，**不是独立证据** ⇒ 已改措辞 |
| 7 | "已证明密钥真随机/在 OTP" | **未证明** —— 只是"有限候选未命中" ⇒ 已降级表述 |
| 8 | S1R2 的四字节生成键"扫满 2^32" | 四字节键**最多 2^32 个不同候选**，模式 0 扩大的是**计数上界**，**不扩大密钥空间** |

## E6. `0x9606` 段落的定级（同事正确，采纳）

原稿把它写成"第 3 优先路线"。**修正**：
> 它仍是**主机程序侧线索**。相机端校验、擦除时序、签名是否覆盖该通路、免擦除入口，
> **均无新增实机消费者证据**。**不因报告建议而进行设备操作。**
> **项目红线不变：永不发送 `0x9406` 子码。**

## 勘误后的净结论

**保留下来的有效成果**：
1. ✅ S5 固件的**同明文对清单**（32 跨版本 + 3 版内），**偏移已修正、内部自洽（0 矛盾）**

5. ✅ 修正后的判据数据（`pairs_s5_FIXED.*`）
