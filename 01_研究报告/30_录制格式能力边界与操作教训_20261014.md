# 录制格式能力边界与操作教训

**日期**：2026-10-14（凌晨实测）
**对象**：Panasonic DC-S5 · 固件 VD4.30 · 相机 IP `192.168.1.131`
**通道**：Wi-Fi `cam.cgi`（`User-Agent: LUMIX Sync`，必须）
**方式**：以 **RAM-only `setsetting`** 为主（不写 flash），全部结论均**回读复核**
**证据目录**：`04_工具与脚本/campaign2/`、`06_数据与证据/camera_settings/`

> 本文有两个目的：
> ① **把既有结论「哪些隐藏录制格式能拿到」验证到穷尽**（既有文档已定性，本文给出实证与机制）；
> ② **记录本次实验发现的操作级问题**（此前无系统记录）。
> 所有数字与档名均来自本次实测输出，无推测成分。

---

## 0. 一句话结论

> **既有结论经穷尽性验证多数仍然成立**（`mov` 态可选档机制正确，唯档数须按制式修正；5.9K/6K/400Mbps 等本机恒隐藏），
> **本机可达上限 = `mov_60p_200mbps_4k_10bit`（NTSC）/ `mov_50p_200mbps_4k_10bit`（PAL），
> 即 200Mbps 4K 10bit，且机身菜单可用。**
> **`a6k` 家族会静默把容器改成 AVCHD，必须禁用。**
> **`setsetting` 返回 `ok` 不等于格式生效——必须回读确认，最终要用实拍文件头验证。**

## 1. 测试环境与前提

| 项 | 值 |
|---|---|
| 机型 / 固件 | DC-S5 / VD4.30 |
| 相机 IP | `192.168.1.131`（主机 `192.168.1.129`） |
| API | `http://192.168.1.131/cam.cgi`，UA 必须 `LUMIX Sync` |
| 相机模式 | `cammode=rec`（录制模式；回放模式下视频域设置器会拒绝） |
| 制式 | **PAL 与 NTSC 都测过**（`ntsc_pal` 决定可用帧率族） |
| 写入方式 | **RAM-only `setsetting`**（`GET ?mode=setsetting&type=videoquality&value=<名>`） |
| 复核方式 | 每次设定后 `getsetting&type=videoquality` **回读**；关键项再等 6–8 秒二次回读 |
| 重试策略 | 遇 `err_reject` 退避重试，最多 8–12 次，间隔 2–3 秒 |
| 健康观测 | `getstate` 全程 `result=ok`、`temperature=low`、`rec=off` |

**注意：回放模式陷阱**：`cammode=play` 时，`setsetting videoquality=<隐藏档>` 一律回
`err_param`，且**已经回 `ok` 的调用也不会生效**。本次实验中有两轮扫描因此作废。
**做视频域实验前必须先确认 `cammode=rec`。**

**模式切换走 API，不要动机身拨盘**：

```
GET /cam.cgi?mode=camcmd&value=recmode     切拍摄模式
GET /cam.cgi?mode=camcmd&value=playmode    切回放模式
```

实测 `recmode` 一次返回 `err_critical`，**重试后即回 `ok`**（状态在翻动，见 §5）。
动机身拨盘会**断开远程连接**，用 API 则不会。

## 3. 5.9K 的穷尽性验证 —— 对「本机恒隐藏」的实证

既有成果文档（`隐藏格式持久化_成果.md` 第 131 行）已把 5.9K / 6K / 100p / 120p / 400mbps
定性为「其他机型占位，**本机恒隐藏**」。**今天的工作是把这句定性验证到穷尽**，
并补上"为什么隐藏"的机制解释（§3.2）——**是补强，不是推翻**。

**四种变量组合全部失败**：

| 变量 | 覆盖 |
|---|---|
| **制式** | PAL ✓ / NTSC ✓ |
| **相机模式** | 视频录制模式 ✓ / **6K PHOTO 模式（原生开 6K 片门）✓** |
| **重试** | 每档最多 **12 次**退避重试 |
| **命名族** | `mov_*_5_9k_10bit` / `mov_5_9k_*_420_10l` / `mov_c24p_*_5_9k_10bit` |

### 3.1 6K PHOTO 模式的实测状态

用户在 6K PHOTO 模式下重新要求尝试，当时相机状态：

```
cammode              = rec
6k4k_photo           = 6k_start_stop     ← 6K 片门全开连拍，工作中
pictsize_burstspeed  = 6k_18m_30p
aspectratio          = 3:2
```

**在这个模式下重测 5.9K，结果依旧是全部失败**（`err_reject` / `err_param`）。

### 3.2 由此得到的关键论点

> **6K PHOTO 模式原生就能开 6K 片门全开** —— 这证明 **传感器的读出能力是具备的（硬件不拦）**。
> 而 5.9K **视频**档依然被拒 ⇒ **这是固件按机型做的市场分层**，不是硬件限制。
> S5 的定位低于 S1H / S1R，那两台才有 6K 视频。

**⇒ 主机侧（API / 菜单 / 参数组合）手段到此为止。**
剩下的唯一理论路径是项目早已定性的那两条：**RAM dump 或绕过固件 AES**——
而固件密钥固化在 MC801 片内，离线 130k+ 探测已被终局否定（见执行摘要阶段一）。

### 3.3 与 10-13 结论的一致性

10-13（晚·续）已用**实拍文件头**做过终判：请求 5.9K 30p，实际产出
`P1000004.MOV` = 4096×2160 @59.94fps ≈195Mbps（C4K 60p），**不是 5888×3312**。
**10-14 的 API 层全面拒绝与之完全吻合**，两条独立证据同向。

### 3.4 注意：前人那次「5.9K 尝试」实为**空操作**（本次复核发现）

复核 `04_工具与脚本/campaign2/out/` 里的落盘文件发现：

```
out/quality_payload_mov_30p_200mbps_5_9k_10bit_20261013_024240.bin
out/backup_pre_quality_20261013_024240.bin
        ⇒ 两者【逐字节相同】（cmp 验证，均 65,533 字节）
```

**⇒ 那一次声称"写入 5.9K 码"的操作，载荷与写入前备份完全一致，
即从未真正改过任何一个码字节。**

**这条很重要**：后人若只看到 `out/` 里有 `quality_payload_mov_30p_200mbps_5_9k_10bit_*.bin`
这个文件名，很容易误以为"5.9K 试过了、不行"。**实际上那次是空的。**

配合 §2.3 的 API 层全面拒绝，**当前对 5.9K 的有效证据只有两条**：

1. **10-13 实拍文件头终判**（`P1000004.MOV` = C4K 60p，非 5888×3312）
2. **10-14 API 层穷尽性拒绝**（本文 §2.3 / §3）

> 同时提示：`02_项目时间线.md` 里「5.9K 30p→码 `0xf4`」这一映射，
> 依据的正是那次空操作，**该码值不可信、不要使用**
> （`隐藏格式持久化_成果.md` 第 133-138 行亦已明确 `0xf4` 是错误值）。

## 4. 菜单变灰的精确条件

### 4.1 判据

> **当 `videoquality` 的当前值不存在于机身菜单定义 `allmenu` 中时，
> 机身【录制质量】整项变灰、不可用。**

本次实验做了**双向对照**：

| 步骤 | `videoquality` | 在 allmenu？ | 机身菜单 |
|---|---|---|---|
| 设入 | `mov_50p_200mbps_c4k_10bit` | 命中 0（curmenu 命中 1） | **变灰** |
| 改回 | `mov_50p_200mbps_4k_10bit` | 命中 4 | **恢复可用** |

### 4.2 菜单读的是 **RAM** 值 —— 双轨方案不成立

曾尝试的方案：**flash 里存 allmenu 安全值（保证菜单可用），RAM 里上隐藏档（拿到格式）**。

**实测证伪。** 当时 flash 里存的确实是 `0x9b`（allmenu 安全），但 RAM 一旦设为
`mov_50p_200mbps_c4k_10bit`，**菜单立刻变灰**。

> **⇒ 菜单读的是 RAM 当前值，不是 flash 值。**
> **"flash 安全 + RAM 隐藏"的双轨方案不成立。**

### 4.3 allmenu / curmenu 的**性质差异**（10-14 复核更正）

> **本节初稿出过错，这里是更正后的正确版本。** 初稿用 `grep mov_*` 从两份文件粗暴提取名字做集合差，
> 得出「curmenu 独有 95 条」——**该数字是伪结论，已作废。**

**根因：两份文件性质根本不同。**

| 文件 | 性质 | 大小 | `cmd_value` 出现次数 |
|---|---|---|---|
| `allmenu.xml` | 相机**菜单树**：`<item ... cmd_type="videoquality" cmd_value="<档名>">` | 307,714 B | **666** |
| `curmenu.xml` | **App 侧可见性快照**：`<item id="menu_item_id_…" enable="yes/no"/>` | 47,162 B | **0** |

`curmenu` 里那批 `mov_*` 字符串大多来自 `title_id` / `img` / `id` 等**标签标识符**，
**不是可执行的菜单项**。拿标签当档位做差集，必然得出荒唐数字。

#### 正确口径与正确数字

**① `allmenu` 里真正可执行的 `videoquality` 项 = 44 个**（mov **31** + mp4 **13**）。

**② `curmenu` 的 `enable` 标志是「当前状态下真正可选」的第一手权威判据，
且与【容器 + 制式】**双重**强相关。**

| 条件 | mov `enable=yes` | mp4 `enable=yes` | mp4hevc `enable=yes` | avchd |
|---|---|---|---|---|
| **NTSC + mov** | **18**（24p 6 + 30p 6 + 60p 6） | 0 | 0 | 0 |
| **PAL + mov** | **12**（25p 6 + 50p 6） | 0 | 0 | 0 |
| **NTSC + mp4** | 0 | **8** | **2** | 0 |
| （存盘那份 `curmenu.xml`，MP4 态抓） | 0 | 5 | —（未统计） | — |

- **「mov 态 17 档可见」是 NTSC 专属数字** —— **PAL 下只有 12 档**。本次实测 NTSC 为 **18**，
  与旧文档的 17 差 1，系是否含「当前选中项」的统计差异。
- **`mp4hevc` 并非不可用**：NTSC + mp4 态下有 **2 档启用**
  （`mp4hevc_24p_72mbps_4k_10bit`、`mp4hevc_30p_72mbps_4k_10bit`）。
  **项目当年「放弃 HEVC」是主动取舍，不是相机不支持**——凡写「HEVC 不可用」处均应加注。
- **NTSC + mp4 态实际可选 = mp4 8 + mp4hevc 2 = 10 档** ⇒ 「16 个 `mp4_*`」既与「声明 13」不符、
  也与「启用 8」不符，**确认是错误数字**。
- 切制式会让相机自动换档：`ntsc → pal` 后画质被自动切成 `mov_50p_100mbps_10bit`，档数由 18 变 12。

**③ mov 态下 `enable=yes` 的 18 个档，就是机身【录制质量】里真正可选的全部 mov 档：**

`mov_24p_100mbps` / `_10bit` / `_4k` / `_c4k`、
`mov_24p_150mbps_4k_10bit` / `_c4k_10bit`、
`mov_30p_100mbps` / `_10bit` / `_4k` / `_c4k`、
`mov_30p_150mbps_4k_10bit` / `_c4k_10bit`、
`mov_60p_100mbps` / `_10bit`、`mov_60p_150mbps_4k` / `_c4k`、
`mov_60p_200mbps_4k_10bit`、`mov_60p_200mbps_c4k_10bit`

（与 10-12 成果文档记的「17 档可见」吻合；差 1 系本次统计含当前选中项。）

**④ 与 `allmenu` 的 31 条声明做差：**

| 集合 | 数量 | 内容 |
|---|---|---|
| `allmenu` 声明 mov 档 | 31 | — |
| mov 态 `enable=yes` | 18 | 上表 |
| **声明了但未启用** | **14** | **全部 `25p` / `50p` 档 + 3 个 `5_9k` 档** |
| **启用但 `allmenu` 未声明** | **1** | **`mov_60p_200mbps_c4k_10bit`（`0x8b`）** |

**⑤ 两条重要推论：**

- **`25p` / `50p` 档未启用，是因为当时制式是 NTSC** —— 这两族是 PAL 档位，被**制式**过滤
  （切到 PAL 后启用的会是另一批）。**⇒ `enable` 集合受「容器」和「制式」双重门控。**
- **「启用但未声明」的档恰好只有 `mov_60p_200mbps_c4k_10bit` 一个** ——
  **这正是 10-13 老文档 `07_隐藏格式持久化_追查_20261013.md:89` 的原结论，它是对的**；
  本次以一手 `enable` 数据独立复现。`0x8b` 令菜单变灰的机制由此完全闭合。

### 4.4 附带发现：另一条"条目可见 ⇄ 菜单变灰"的路径

10-13（晚·续3）已记录：`mp4ed`（`0x07`）容器未在 `allmenu` 中声明时，
**【录制文件格式】与【录制质量】两项一起变灰**，且当前值会被渲染成一个多余的 "(LPCM)" 条目。

> **本条与 §4.1 是同一机制的两个表现面**：条目可见与菜单变灰是**同一失配的两面**，无法同时满足。
> 且 **S5 没有 S1H 的"添加到列表（My List）"** —— 全量菜单扫描无任何 list 项，
> 因此**无法把隐藏档"注册"成常规菜单入口**。

## 5. 机制：存在比 `allmenu` 更严格的第二层过滤

**该观察为过滤层提供了一个结构性解释。**

`mov_30p_200mbps_5_9k_10bit` **在 `allmenu` 里有声明**（菜单条目的数据源），
但 `setsetting` 依然返回 **`err_reject`**，即使退避重试 12 次也不通过。

**⇒ 结论：**

> **"`videoquality` ∈ `allmenu`" 只是"菜单不变灰"的【必要】条件，
> 不是"设置器接受它"的【充分】条件。**
> 设置器背后还有一层更严格的过滤（很可能与机型能力表 / 传感器读出模式相关）。

**佐证**：`capability.xml`（`06_数据与证据/camera_settings/`）中**完全不含** 5.9K / 6K / og6 / opengate
任何字样——它只声明 `camcmdlist`、`camspeclist`、`asst_disp`、`stopmotiontset`、`contents_action_info` 等。
**⇒ 该层过滤不在 `capability.xml` 里，位置待定。**

|---|---|---|
| **NTSC（菜单可用）** | `mov_60p_200mbps_4k_10bit` | **200Mbps 4K 10bit** |
| **PAL（菜单可用）** | `mov_50p_200mbps_4k_10bit` | **200Mbps 4K 10bit** |
| NTSC（接受菜单变灰，换 C4K） | `mov_60p_200mbps_c4k_10bit` | 200Mbps C4K 10bit |
| PAL（接受菜单变灰，换 C4K） | `mov_50p_200mbps_c4k_10bit` | 200Mbps C4K 10bit |

> **`mov_60p_200mbps_4k_10bit`（NTSC）/ `mov_50p_200mbps_4k_10bit`（PAL）
> = 200Mbps 4K 10bit，且菜单可用 —— 这就是本机的实际天花板。**
> 与 C4K 档的差别仅在**裁切画幅（4K vs C4K）**，码率与位深相同。

**达不到的**：5.9K、6K、400Mbps、`a6k`。理由见 §2、§3、§5。

### 6.1 质量码对照（**引用既有成果，勿另行推算**）

上述档位在 camsetting blob `6986` 处的编码，以
`04_工具与脚本/campaign2/隐藏格式持久化_成果.md`（§关键结论 2）为准：

| 码 | 档名 |
|---|---|
| `0x8b` | `mov_60p_200mbps_c4k_10bit`（C4K 顶档） |
| `0x9b` | `mov_60p_200mbps_4k_10bit`（4K 档） |
| `0x92` | `mov_60p_150mbps_c4k`（机身菜单安全档） |
| `0xc1` | `mp4_30p_20mbps`（mp4 容器默认） |

> **不要使用 `0xf4`** —— 旧文档曾把 5.9K 30p 记为该码，**该值已确认是错误值**，
> 且其依据是一次空操作（见 §3.4）。

## 7. 错误码语义（实测补充）

| 返回 | 语义 | 正确处置 |
|---|---|---|
| **`ok`** | 请求被接收 | **注意：不等于生效！必须回读 `getsetting videoquality` 确认** |
| **`err_reject`** | 参数格式**对**，但相机**当前状态不接受** | **退避重试**（状态在翻动），8–12 次、间隔 2–3 秒 |
| **`err_param`** | 参数格式被拒（档名不存在 / 不适用） | 不要重试，检查档名 |
| **`err_busy`** | 相机忙 | 退避重试 |
| **`err_critical`** | 严重状态错误 | 先重试一次（实测 `recmode` 重试即 `ok`），仍失败则重启相机 |

### 7.1 `ok` 返回值不可靠：本次实验记录到至少 6 次例外

| 档名 | 返回 | 真实结果 |
|---|---|---|
| `mov_25p_200mbps_5_9k_10bit` | `ok` | 未生效 |
| `mov_30p_200mbps_5_9k_10bit` | `ok` | 未生效 |
| `mov_24p_200mbps_5_9k_10bit` | `ok` | 未生效 |
| `mov_24p_200mbps_6k_10bit` | `ok` | 未生效（反而被相机换成 `mov_60p_200mbps_c4k_10bit`） |
| `mov_25p_200mbps_a6k_10bit` | `ok` | 危险：**改成 AVCHD** |
| `mov_25p_150mbps_a6k_10bit` | `ok` | 危险：改成 AVCHD |
| `mov_25p_100mbps_a6k` | `ok` | 危险：改成 AVCHD |

### 7.2 `err_reject` 需退避重试：实测证据

```
setsetting videoquality=mov_50p_200mbps_4k_10bit
  尝试 1: err_reject   回读=mov_50p_200mbps_c4k_10bit
  尝试 2: err_reject   回读=mov_50p_200mbps_c4k_10bit
  尝试 3: err_reject   回读=mov_50p_200mbps_c4k_10bit
  尝试 4: err_reject   回读=mov_50p_200mbps_c4k_10bit
  尝试 5: ok           回读=mov_50p_200mbps_4k_10bit   ← 第 5 次才成功
```

同一天的 `camcmd&value=recmode` 也先回 `err_critical`、重试后回 `ok`。
**⇒ 单次调用会把成功误判为失败。**

## 8. 操作级教训汇总（配合 `25_操作记录与风险手册` 使用）

1. **`ok` 完全不可信** —— 必须回读 `getsetting videoquality` 确认，最终用**实拍文件头**终判。
2. **`err_reject` 要退避重试** —— 8–12 次、间隔 2–3 秒。
3. **⛔ 禁用 `a6k` 家族** —— 返回 `ok` 却静默把 `videoformat` 改成 `avchd`。
4. **模式切换走 API**（`camcmd&value=recmode` / `playmode`），**不要动机身拨盘**（会断远连）。
5. **视频域实验前先确认 `cammode=rec`** —— `cammode=play` 时设置器拒绝、且已回 `ok` 的也不生效。
6. **写 flash 后不能用"立即回读"当成功判据** —— `getinfo camsetting` 返回的是 **RAM 副本**，
   只有**断电重启后**的回读才代表 flash 内容。

#### 原「三点机制刻画」

1. **声明数 ≠ 可选数** —— `allmenu` 声明 31 个 mov 可执行档，但 mov 态下真正 `enable=yes` 的只有 **18** 个（§4.3）
