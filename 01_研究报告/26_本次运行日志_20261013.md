## [第 2 阶段] exFAT 越界写验证（含一次撤回）

### 2026-10-13 17:3x–18:0x — 第 1 级：前置条件确认

- **目的**：验证内核释放簇时是否跟随卡上 FAT 值
- **方法**：改被删文件的**链尾 FAT 值**指向"不属于它的簇"，删除后比对**分配位图**
- **执行结果**（最终有效的一组）：
  ```
  被删文件 P1000024.JPG 链 39–111（73 个簇）
  注入 FAT[111] = 4（根目录所在簇）
  卡指纹一致 boot_ck=0x2668BB77 / ClusterCount=488288
  被释放 78 个簇，其中【注入目标簇 4 在释放列表 = True】
  ```
- **注意事项**：必须用**位图前后比对**当证据，不能只看相机报错
- **风险**：改错 FAT 会破坏文件链
- **验证**：卡指纹一致 + 注入簇不属于被删文件却出现在释放列表
- **回滚**：`setfat` 还原
- **结论**：✅ **内核对簇号不做归属校验，释放路径完全跟随卡上 FAT 链值**

### 2026-10-13 18:0x — 第 2 级：越界注入（**后被撤回**）

- **目的**：把注入值换成越界值，触发 `vol_amap[i]` 越界
- **命令**：`go2`（注入 `524290` → 索引 128 ≥ map_sectors 120）
- **执行结果**：相机报**「写入错误 请检查卡」**，**未死机**
- **当时的推理（错误）**：`clr_alloc_bitmap()` 先内存写、后卡写 ⇒ 报卡写失败 ⇒ 内存写必已执行
- **风险**：可能内核崩溃

### 2026-10-13 18:1x — 堆喷尝试（三轮，全部失败）

| 轮次 | 做法 | 结果 |
|---|---|---|
| 1 | 240 个 240 字符长名（+240 个 macOS `._` 副档名） | 相机反复重启 → **误判为堆喷命中** |
| 2 | 120 个 240 字符长名 + 越界注入 | 「写入错误」 |
| 3 | 120 个短名 + 篡改 `num_ext` + 越界注入 | 「写入错误」 |

- **A/B 对照（关键）**：**去掉注入后照样重启** ⇒ 第 1 轮的"重启"**不能归因于注入**
- **结论**：撤回"堆喷命中"
- **方法论教训**：**没有对照组的结论不要写进报告**

### 2026-10-13 19:2x — 决定性实验：推翻"越界写已执行"

- **目的**：区分"空指针提前返回"与"有效指针 + 卡写失败"
- **命令**：`go2 auto 491522` → 索引 `(491522-2)>>12 = 120`，落在 **slab 填充区（必为 NULL）**
- **执行结果**：相机**只报"写入错误"，未崩溃**

- **影响**：❌ **撤回"S5 越界写已实机确认"**
- **附带发现**：**S1R2 报告用的判据（相机报写入错误 = 内存写已执行）本身有漏洞**，不应被后人照抄

|---|---|---|---|
| T1 | ~20 | 240 字符 | ✅ |
| T2 | 241 | 12 字符 | ✅ |
| T3 | 241 | 240 字符 | ✅ |

- **结论（当时）**：阈值在 241–480 个长名目录项之间

### 2026-10-13 19:2x — ⚠️ **发现工具把卡写坏了**

- **症状**：照片"文件在、但无法访问/无法删除"
- **诊断命令**：`chain 39`
- **执行结果**：
  ```
  照片 P1000123.JPG 应为 39→40→…→115（77 簇）
  实际: 39 → 482 → 483 → 0xFFFFFFFF      ❌ 只有 3 簇
  目录簇链: [38, 39]                      ❌ 目录被"扩展"到了照片的数据簇上
  ```
- **根因**：`alloc_one_cluster()` **只信分配位图**；相机位图**延迟写回**（未正常关机就拔卡）⇒ 分配器拿到**照片正在使用的簇**
- **影响**：
  1. 照片被毁
  2. **当时的"长名崩溃"结论被污染**（目录链被打乱后内核遍历到垃圾/环，很可能是重启真因）
- **修复**：分配器改为**三重校验**（**位图位=0 且 不在目录链 且 FAT[clu]==0**）
- **新增规矩**：
  - **拔卡前必须在相机里正常关机**
  - **每次写卡前后都跑 `checkalloc`**

### 2026-10-13 19:2x — 位图可信性验证

- **命令**：`checkalloc`（新卡：相机格式化 + 2 张照片）
- **执行结果**：`位图 194 簇 / FAT 190 簇 / 位图说空闲但FAT非0 = 0 个` ⇒ **一致** ✅
- **结论**：位图本身可信；问题出在**拔卡时机**导致的滞后

### 2026-10-13 19:2x–19:3x — 干净定因实验（四组矩阵）

| 组 | 文件数 | 名字长度 | entry set | 条目数 | 体量 | 相机 |
|---|---|---|---|---|---|---|
| A | 241 | 240 | 576 B | 2169 | 139 KB | ✅ |
| **B** | **360** | **240** | 576 B | 6480 | 202 KB | ❌ **崩** |
| C | 2160 | 12 | 96 B | 6480 | 202 KB | ✅ |

- **B vs C** ⇒ 排除"条目数/目录体量"
- **B vs D** ⇒ 排除"entry-set 分配大小"
- **结论**：✅ **触发条件是「240 字符长文件名 × 约 300+ 个文件」本身**

- **每组的前置/后置校验**（都通过）：

## [第 6 阶段] S5 无线监看工具（2026-10-13 22:xx）

### 2026-10-13 22:xx — 从零做出监看工具并实机打通

- **目的**：复刻 LUMIX Flow 的"手机当监视器"，让 S5 也能用
- **产物**：`04_工具与脚本/s5_monitor/`（`s5monitor.py` + `www/index.html` + `run.sh` + `README.md`）
- **实机验证通过** ✅：
  - 取景流：**640×432 MJPEG，18.7–19.8 fps**（UDP 49152）
  - **触摸对焦 ✅**、**拍照 ✅**、峰值/放大辅助 ✅、AE 锁定 ✅、回放切换 ✅

### 关键实测发现（都写进了 README）

| # | 发现 |
|---|---|
| 1 | **`camctrl type=touch` 的坐标必须用 `/` 分隔**，且**必须带 `value2=on`**（用逗号或缺 value2 ⇒ `err_param`）—— 从官方 APK 源码核对出来 |
| 2 | **`camctrl type=focus` 是【变焦】不是对焦**（`tele-normal`/`wide-fast`/`focus-stop`…） |
| 3 | **相机强制单流会话**：上次没 `stopstream`，新的 `startstream` 返回 `err_busy` ⇒ 必须先 stop 再 start + 退避重试 |
| 4 | **心跳与取景流互斥**：`getstate` 耗时 1–3 秒，期间取景流被挤停；<br>完全不发心跳则约 13 秒后停流 ⇒ **最优 10 秒一次 + 状态走服务端缓存**（实测 45 秒零停顿） |
| 5 | **`camctrl` 会整通道 `err_busy`**（`camcmd`/`getstate` 仍正常）⇒ 需相机处于实时取景激活状态 + 退避重试 |
| 6 | **取景流无画质参数**（`startstream` 只有端口）⇒ **640×432 是硬上限**，要清晰画质只能走 HDMI |

### 错误码语义（实测）

`err_param` = 格式错 / `err_reject` = 状态不接受 / `err_busy` = 相机忙（退避重试）/ `err_critical` = 严重

### 意义

**官方 LUMIX Flow 不支持 S5**（只面向 S9/GH7/S5II 等新机型），
但 S5 硬件自带取景推流能力 ⇒ 本工具把 **LUMIX Flow 最有价值的"手机监看 + 触摸对焦"** 在 S5 上补了回来。


### 2026-10-13 22:xx — 卡顿根治（节奏缓冲器）

- **现象**：画面每 0.5–0.75 秒卡一下
- **定位方法**：逐 250ms 采样相机侧收帧数 → 发现**突发模式**（`0,8,6,0,0,2,16,8,0,...`，250ms 内最多 16 帧）
- **排除**：`getstate` 实测只占 0.07s，**不是心跳的锅**
- **修复**：服务端加**节奏器** —— 帧队列(24帧) + 20fps 匀速发布 + **空档重播上一帧**；另加 `TCP_NODELAY`、单次 write、8MB UDP 缓冲、状态缓存

**最终方案**：队列长度比例控制（`RESERVE_TARGET=8`、`PACING_KP=0.6`、`ARRIVAL_EMA=0.25`）

### 8.2 ★★ 找到的关键规律：**`req_acc` 只能发一次**

**这是本次排查最重要的发现，也解释了此前所有"时好时坏"的现象**：

```
每调用一次 accctrl&type=req_acc
   ⇒ 相机上产生一条【待批准】消息
   ⇒ 会话状态从  ok  退回  ok_under_research_no_msg（受限）
```

- **之后永不重发** —— 否则会把已经批准的会话打回受限模式
- **服务重启 = 重新 req_acc = 需要重新在相机上批准**

**⇒ 这条直接解释了**：
1. "最开始能用、后来不能用" —— 早期批准后是 `ok`，之后我们所有测试都在重发 `req_acc`
2. 项目报告 16 记录的"状态在 `ok` 与 `ok_under_research_no_msg` 间跳动"
3. 为什么"拍照/录像一直能用、camctrl 时好时坏"（camcmd 不受会话等级限制）

**已修复**：`/api/access` 不再重发 `req_acc`；`ensure_access` 只发一次并等待批准。
