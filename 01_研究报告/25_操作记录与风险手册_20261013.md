# 操作记录与风险手册

> **用途**：本文件记录 DC-S5 逆向项目中**每一项实际操作**的命令、作用、前置条件、
> 注意事项、风险、验证方法与回滚方法。
>
> **规矩**：**今后每一步操作都要在此留一条记录**（模板见 §9）。
> 目的不是走形式，而是 —— 本项目已经出现过两次"因为没记清操作前提，
> 导致结论被污染、被迫撤回"的情况（见 `23_` §0.5 与 `24_` §6.1）。

## 1. 通用铁律（任何操作前先过一遍）

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **写 flash 必须 AC 供电** | 断电写 flash 有砖机风险 |
| 2 | **永不刷真实固件** | 变砖不可恢复 |
| 3 | **永不 `resetDevice`、永不写 PTP 配置回写（`0x9422`/`0x9423`/`0x9406` 子码）** | 不可逆 |
| 4 | **改 `camsetting` 前必须退出机身菜单**，否则 `err_reject` | 相机设计 |
| 5 | **拔 SD 卡前必须在相机里正常关机** | 相机分配位图**延迟写回**；直接拔卡会让位图停在旧状态，后续任何按位图分配的工具都会**踩到正在使用的簇** |
| 6 | **任何写卡操作前后各跑一次 `checkalloc`** | 确认位图与 FAT 一致（`K=0`） |
| 7 | **同一张卡不要在两次实验之间"叠加"状态** | 每轮实验从**相机格式化**开始 |
| 8 | **服务模式只读**，不点任何会写标定的项 | 部分项（地区后缀）**一次性写入、不可逆** |
| 9 | **`4kcrop` 相关项禁碰** | 已知高风险 |
| 10 | **崩溃后先拔卡**，相机通常会立刻恢复 | 大多数崩溃是卡引起的 |

## 2. 环境与权限（macOS 侧）

| 项 | 事实 | 影响 |
|---|---|---|
| 原始磁盘设备 | `brw-r----- root:operator` | 普通用户读不到；本项目主用户**不在** `operator` 组 |
| TCC | 原始磁盘访问还需进程具备**「完全磁盘访问」** | 即使用 `osascript` 提权到 uid=0 仍报 `Operation not permitted` |
| 结论 | **所有读写原始设备的命令必须由人在终端里 `sudo` 执行** | 自动化/AI 进程两条路都过不去 |
| `osascript` 提权后的 root shell | **访问不了 `~/Documents` 等受保护目录**（`Operation not permitted (126)`） | 脚本要放在 **`/tmp`** 下执行 |
| 设备节点 | **卡拔插后会变**（`disk8s1` → 可能变 `disk9s1`） | 脚本需按"卷名 + 文件系统 + 容量"自动重新识别 |

**推荐的一次性放宽**（可选）：

```bash
# 让当前用户能【只读】原始设备（写仍需 root）
sudo dseditgroup -o edit -a $(whoami) -t user operator
# 或在「系统设置 → 隐私与安全性 → 完全磁盘访问权限」里勾选所用终端
```

## 3. SD 卡相关操作

### 3.1 识别目标卡

```bash
ls -l /dev/disk*s*                       # 看容量与时间戳
diskutil info /dev/diskNsM | grep -E "Volume Name|Disk Size|File System Personality"
```

| 注意事项 | |
|---|---|
| **32GB 及以下（SDHC）相机只按 FAT32 用** | exFAT 漏洞只在 exFAT 路径上，**SDHC 用不了** |
| **Mac 格式化的 exFAT 相机不认** | 会提示"记忆卡错误需要格式化" → 让相机自己格式化 |
| 两张卡卷名可能都叫 `LUMIX` | 靠**容量**区分（64.0 GB vs 31.9 GB） |

**风险**：无（只读）。
**回滚**：无。

---

### 3.2 格式化卡

```bash
# Mac 侧（把卡清成 exFAT，供相机重建）
diskutil unmountDisk force /dev/diskN
diskutil eraseVolume ExFAT LUMIX /dev/diskN sM
```

| 注意事项 | |
|---|---|
| Mac 格式化后相机**不认**，会要求重新格式化 | 这是**预期的**：相机格式化会重建它自己的布局 |
| **相机内格式化**才是"原生可用的干净状态" | 每轮实验都从这一步开始 |

**风险**：**丢失卡上全部数据**（实验卡，可接受）。
**验证**：`diskutil info` 应显示 ExFAT。
**回滚**：无法恢复数据。

---

### 3.3 创建测试目录项（核心工具）

```bash
# 体检（必须先 K=0）
sudo bash /tmp/s5exfat/s5_exfat_test.sh checkalloc /dev/disk8s1

# 写 N 个指定名字长度的目录项（会自动分配数据簇）
sudo bash /tmp/s5exfat/s5_exfat_test.sh mkentries /dev/disk8s1 <数量> <名字长度> [起始序号]

# 短名字 + 篡改 num_ext（精确控制内核分配大小）
sudo bash /tmp/s5exfat/s5_exfat_test.sh mkspray  /dev/disk8s1 <数量> <num_ext> [起始序号]

# 已删除条目填充（只占空间、不产生分配）——用于对照实验
sudo bash /tmp/s5exfat/s5_exfat_test.sh mkdeleted /dev/disk8s1 <数量>

# 原地清场（从第 N 个槽位起清零，不用重新格式化）
sudo bash /tmp/s5exfat/s5_exfat_test.sh trimdir  /dev/disk8s1 <保留槽位数>
```

| 注意事项 | |
|---|---|
| **先看 `目录簇链` 那行** | 新分配的目录簇必须落在**照片数据区之后**；若出现像 `[38, 39]` 这种"新簇紧贴/落在照片范围"，**立即停手** |
| **写后必须再跑 `checkalloc`** | `K` 必须仍为 0；分配数增量应等于「文件数 + 目录扩展簇数」 |
| `mkentries` 每个条目**占一个数据簇** | 2160 个 ≈ 270 MB，注意容量 |
| `trimdir` **只清零目录项，不释放数据簇** | 数据簇保持占用（可接受） |

**风险**：
- ⚠️ **若分配器踩到正在使用的簇 ⇒ 照片/文件被毁、目录链被打乱**（本项目**真实发生过一次**，见 `24_` §6.1）
- ⚠️ **相机可能进入反复重启**（预期内的实验结果，不是故障）

**验证**：`checkalloc` 两次都 `K=0`；`entries` 能列出预期的文件名与簇号。
**回滚**：`trimdir` 清场；或整卡重新格式化。

### 3.4 相机侧操作与崩溃恢复

| 操作 | 注意事项 |
|---|---|
| 插卡开机 | 若按预期重启，说明实验结果成立 |
| 删除照片 | 只有在"注入 FAT 链尾"的实验中才需要；此时删除**会失败**（这是判据，不是故障） |
| **关机** | **必须正常关机再拔卡**（位图落盘） |

**崩溃（反复重启）恢复流程**：

```
① 从相机里拔出卡          → 相机应立刻恢复正常
② 卡插回 Mac
③ diskutil eraseVolume ExFAT LUMIX /dev/disk8s1
④ 插进相机 → 让相机自己格式化 → 继续下一轮
```

**风险**：无硬件损伤（崩溃是软件层）。
**回滚**：格式化即可，**卡可完全恢复**。

## 4. FAT 补丁相关操作（exFAT 越界写一线）

| 命令 | 作用 | 风险 |
|---|---|---|
| `prep` / `info` / `entries` / `chain` / `bitmap` | **只读**诊断 | 无 |
| `dumpbitmap <文件>` | 位图落盘 + 写卡指纹 | 无（只读卡） |
| `setfat <簇> <值>` | **精确改一个 FAT 项**（带 fsync + 重开设备复核） | 改错会破坏文件链 |
| `go1` / `go2` / `session` / `sessionA` / `hijack` | 自动挑目标 + 打补丁 + 回读校验 | **会让目标文件"删不掉"**；`hijack` 还会**吞掉后续目录项** |
| `verdict` / `go1check` | 比对与裁决（含**卡代次守卫**） | 无 |

| 注意事项 | |
|---|---|
| **必须 `fsync` 落盘 + 用新文件描述符回读** | 块设备写入会停在页缓存，**拔卡就丢**（这是早期"补丁没生效"的真凶） |
| **卡指纹守卫**：`BootChecksum + ClusterCount` | 基线/新位图指纹不一致 ⇒ **拒绝裁决**（否则会把"重新格式化过的新照片"误算成释放簇） |
| `hijack` 会**覆盖紧随其后的目录项** | 会"吞掉"约 `num_ext` 个后续文件 |
| **`go2` 的越界注入会让目标文件永久删不掉** | 需 `setfat` 还原或格式化 |

**关键教训（必须记住）**：

> **"相机报写入错误"不能作为"内存写已执行"的判据。**
> `clr_alloc_bitmap()` 里存在 `if (vol_amap[i] == NULL) return -EIO;` ——
> NULL 槽会**提前返回、根本不碰内存**，而相机屏幕上的表现与"内存写成功但卡写失败"**完全一样**。
> （决定性实验见 `23_` §0.5）

**回滚**：
```bash
# 还原单个 FAT 项（原值在 /tmp/.exfat_patch_backup.json）
sudo bash /tmp/s5exfat/s5_exfat_test.sh setfat /dev/disk8s1 <簇号> 0xFFFFFFFF
```

## 8. 每次操作的标准动作清单

```
□ 读一遍 §1 通用铁律
□ 确认设备节点（容量 + 文件系统），不是另一张卡
□ 写卡前：checkalloc（必须 K=0）
□ 执行操作，保存完整输出
□ 写卡后：checkalloc（必须 K=0），并核对分配数增量

□ 记录到运行日志（§9 模板）
□ 出现异常：先拔卡 → 再诊断，不要继续叠加操作
```

## 10. 本项目的连续踩坑清单（写工具/写脚本的人必读）

| # | 坑 | 真相 |
|---|---|---|
| 1 | **Boot Checksum 覆盖范围** | 是**整个引导区 11 个扇区**（跳 106/107/112），**不是 512 字节**。照字面算会错，相机判"卡不可用" |
| 2 | **必须 `fsync`** | 块设备写入停在页缓存，拔卡就丢 |
| 3 | **回读要用新 fd** | 同一 fd 可能命中缓存 |
| 4 | **卡拔插后设备节点会变** | 按卷名+文件系统+容量自动重新识别 |
| 5 | **卡代次守卫** | `BootChecksum + ClusterCount` 当指纹，不一致就拒绝裁决 |
| 6 | **exFAT 文件名在 entry 偏移 2** | 前 2 字节是类型 + 标志 |
| 7 | **"自身链"要排除注入值** | 链集合若在打补丁后才记录，会掩盖结论 |
| 8 | **bash 变量紧邻全角字符** | `$VAR（` 会被当成变量名一部分，`set -u` 下报 `unbound variable` —— 一律写 `${VAR}` |
| 9 | **macOS 会生成 `._` 副档名文件** | 每个文件变两个目录项，**名字还更长** ⇒ 实验变量翻倍。造测试文件后必须 `rm -f ._*` |
| 10 | **分配器只信位图会踩雷** | 相机位图**延迟写回**；必须**位图 + 目录链 + FAT 三重校验** |
| 11 | **"相机报写入错误" ≠ "内存写已执行"** | 可能有 NULL 提前返回 |
| 12 | **不要用 macOS 造超长文件名做实验** | 相机不认（不 stat），且 `._` 会翻倍 |

## 11. 录制格式操作要点（2026-10-14 实测）

> 来源：`01_研究报告/30_录制格式能力边界与操作教训_20261014.md` 与
> `01_研究报告/31_录制格式持久化_受控复测_20261014.md`（DC-S5 / VD4.30 实测）。
> 本节记录**操作层面**的注意事项，与"能力边界"结论分开放置。

### 11.1 `ok` 返回值不可靠，必须回读确认

`setsetting` 返回 `<result>ok</result>` **只代表请求被接收，不代表设置生效**。

**本次实验记录到至少 6 次反例**：

| 档名 | 返回 | 真实结果 |
|---|---|---|
| `mov_25p_200mbps_5_9k_10bit` | `ok` | 未生效 |
| `mov_30p_200mbps_5_9k_10bit` | `ok` | 未生效 |
| `mov_24p_200mbps_5_9k_10bit` | `ok` | 未生效 |
| `mov_24p_200mbps_6k_10bit` | `ok` | 未生效（相机改成了别的档） |
| `mov_25p_200mbps_a6k_10bit` | `ok` | **容器被改成 AVCHD**（危险） |
| `mov_25p_150mbps_a6k_10bit` | `ok` | **改成 AVCHD**（危险） |
| `mov_25p_100mbps_a6k` | `ok` | **改成 AVCHD**（危险） |

**标准动作**：每次 `setsetting type=videoquality` 之后，**必须紧跟一次**
`getsetting type=videoquality` 回读比对。终判要用**实拍文件头**（`tkhd`/`stsd` + `stts` 帧率）。

### 11.2 `err_reject` 要退避重试（不是失败）

`err_reject` = 参数格式**对**，但相机**当前状态不接受** —— 授权/状态在 `ok` 与受限之间**翻动**。

**实测证据**（`mov_50p_200mbps_4k_10bit`）：

```
尝试 1: err_reject   尝试 2: err_reject   尝试 3: err_reject
尝试 4: err_reject   尝试 5: ok          ← 第 5 次才成功
```

同一天 `camcmd&value=recmode` 也是先 `err_critical`、重试后 `ok`。

**建议**：最多 **8–12 次**，间隔 **2–3 秒**。**单次调用会把成功误判为失败。**

### 11.3 禁用 `a6k` 家族：会静默改变容器状态

`mov_*_a6k_*` 档（如 `mov_25p_200mbps_a6k_10bit`、`mov_25p_150mbps_a6k_10bit`、`mov_25p_100mbps_a6k`）
返回 `ok`，**却把 `videoformat` 从 `mov` 静默改成 `avchd`**（`videoquality` 变成 `avchd_50p_28mbps`）。

**不报错、只改状态** —— 没有回读复核的话，使用者会以为"设成了 a6k 档"，实际相机已跳到 AVCHD。

**恢复方法**（实测 1 次即成功）：

```
GET /cam.cgi?mode=setsetting&type=videoquality&value=mov_60p_200mbps_4k_10bit
```

写合法 mov 质量档会**同时把 `videoformat` 带回 `mov`**。

### 11.4 模式切换走 API，不要动机身拨盘

```
GET /cam.cgi?mode=camcmd&value=recmode     切拍摄模式
GET /cam.cgi?mode=camcmd&value=playmode    切回放模式
```

**动机身拨盘会断开远程连接**，用 API 则不会。
（首次调用可能回 `err_critical`，**重试即 `ok`**，见 §11.2。）

### 11.5 视频域实验前先确认 `cammode=rec`

`cammode=play`（回放模式）时：

- `setsetting videoquality=<隐藏档>` 一律回 `err_param`
- **已经回 `ok` 的调用也不会生效**

本次实验中有两轮扫描因此整轮作废。**先跑** `getstate` 确认 `cammode=rec`。

### 11.6 写 flash 后不能用"立即回读"当成功判据

`getinfo camsetting` 返回的是相机设置的 **RAM 副本**，不是 flash 内容。

- "写完立刻回读看到新值" ⇒ 只能说明**RAM 被更新**，**不能证明 flash 已落地**
- **只有「断电重启之后」的回读才代表 flash 内容**

⇒ 由此产生的推论：**不能以"写完立刻回读"判定持久化是否成立**。
> 该项目历史上曾两次据此得出方向相反的结论（先判"持久化成立"，后改判"仅 `ntsc_pal` 持久"），
> 经 2026-10-14 受控复测（n=2）确认：**后一次改判未被重现**——`ntsc_pal`、`videoformat`、`videoquality`
> 三项在断电重启后均保留，唯 `videoquality` 与开机时 SD 卡槽 1 的挂载状态相关。详见 31 号报告。

### 11.7 `req_acc` 只能发一次

`accctrl&type=req_acc` 是**配对/申请授权**，相机对其有**频率/次数保护**：

```
短时间多次 req_acc ⇒ 相机弹「智能手机应用程序需要更新」⇒ invalid login ⇒ 须重启相机
```

**正确做法**：`req_acc` **只在服务启动时发一次**，之后只轮询 `getstate` 等待。
（详见 `12_S5无线监看_v1.0_20261014/附_技术参考.md` §五。）

### 11.8 本机录制格式可达上限（速查）

| 用途 | 档名 | 规格 |
|---|---|---|
| NTSC（菜单可用） | `mov_60p_200mbps_4k_10bit` | 200Mbps 4K 10bit |
| PAL（菜单可用） | `mov_50p_200mbps_4k_10bit` | 200Mbps 4K 10bit |
| 接受菜单变灰 | `mov_60p/50p_200mbps_c4k_10bit` | 200Mbps C4K 10bit |

**拿不到的**：5.9K、6K、400Mbps、`a6k`（穷尽性验证，见 30 号报告 §2、§3、§5）。

### 11.9 写入 flash 前确认槽 1 已挂载

`getstate` 的 `sd_memory` 应为 `set`。

**依据**：受控对照（T1 vs T2，写入值相同，唯一差异为开机时槽 1 的挂载状态）显示，
槽 1 未挂载时 `videoquality` 在**开机阶段**由 `0x9b` 降为 `0x9f`（200 Mbps 10-bit → 150 Mbps）；
槽 1 已挂载时 `0x9b` 保留。`ntsc_pal` 与 `videoformat` 在该对照中均保留。

**注意**：该对照仅 **1 组（n=1 组）**，机制假设（相机依可用介质的写入能力限制录制画质）**待重复实验确认**。
旁证：槽 1 未挂载时 `remaincapacity` 与 `video_remaincapacity` 均为 `-1`；挂载后恢复有效值。

### 11.10 采用"仅写槽 0"的 blob 形态

`0x005e` 记录（偏移 3056）结构为 `[6 字节头 5e 00 14 00 01 00][13 字节槽][1 字节终止 0x00]`。

- **相机自身行为 = 仅写槽 0**（槽形态 `06 05 ×12`），实测重启后保留（n=2）
- `experiment_mov_shadow.py` 的**全槽写**（`06 ×13`）在重启后回退为 `05 ×13` + `videoformat=mp4`（n=1）

**该相关性的因果未确立，列为待验证假设**；操作上**建议采用相机自身行为，即仅写槽 0**。
详见 `01_研究报告/31_录制格式持久化_受控复测_20261014.md` §4.1。

**另**：`0x005e` 的槽形态可用作"写入是否落地"的判别签名（见 31 号 §3.2）。

### 11.11 尝试隐藏档失败后应设回 allmenu 内档位

实测：设置 5.9K / 6K 等被拒档后，相机可能自行停在一个 **curmenu 独有**档
（如 `mov_60p_200mbps_c4k_10bit`），该档**不在 `allmenu` 内 ⇒ 机身【录制质量】整项变灰**。

**处置**：随后用一条 allmenu 已声明档（如 `mov_60p_200mbps_4k_10bit`）覆盖即可恢复正常。
